## Context

See [proposal.md](proposal.md) for scope. This change owns the reputation decisions approved on 2026-10-05 and previously placed in `record-future-product-architecture`. It is an implementation proposal, not evidence that reputation has shipped. The approved compensation direction is retained below as a future Finance integration contract.

Core collection already supplies immutable TaskInputs, submitted QuestionResponses, attempt provenance, append-only ReviewDecisions, frozen Projects, and sealed exports. `QuickTrain.Tasks.Reviews.QuestionReview.initial_decisions!/2` automatically accepts answered submissions, so acceptance alone is not correctness evidence. `QuickTrain.Tasks.Access.WorkerEligibility` currently serves both allocation and existing-attempt authorization; putting reputation restrictions directly into that shared filter would revoke work already issued. `AttemptAllocation` also replays allocation request keys before selecting new work. These are concrete integration boundaries for this change.

The [worker-reputation delta](specs/worker-reputation/spec.md) defines the new behavior; [projects](specs/projects/spec.md) and [task-allocation](specs/task-allocation/spec.md) extend the implemented collection contract. This change does not depend on media execution or Finance.

The specs own behavioral requirements and scenarios. This design records implementation choices, rationale, and unresolved decisions; the [tasks](tasks.md) link those contracts to delivery work.

## Goals / Non-Goals

**Goals:**

- Keep authoritative evidence in its owning domain and make assessments reproducible, scoped, and explainable.
- Implement known-answer checks and conservative peer comparison using existing immutable task identities and typed answers.
- Make project restrictions recoverable without coupling them to account bans, answer acceptance, or payment.
- Use Ash resources, actions, relationships, policies, constraints, and generators; use existing Oban infrastructure for recalculation where asynchronous work is appropriate.

**Non-Goals:**

Follow the [proposal's scope exclusions](proposal.md#what-changes). In particular, do not add a general policy engine, duplicate evidence stream, separate automatic-suspension projection, or speculative Finance adapter/plugin interface.

## Decisions

### 1. Separate evidence dimensions and assessment scope

Add `QuickTrain.Reputation` for derived assessments and their evaluation workflows. Use the existing global User and authoritative Attempts, QuestionResponses, skips, and ReviewDecisions. Preserve contribution provenance without copying source records into a parallel event store.

The [scoped-assessment contract](specs/worker-reputation/spec.md#requirement-scoped-assessments-preserve-evidence-and-uncertainty) defines separate metrics, the three evidence states, and independent refresh metadata. The [source-fact contract](specs/worker-reputation/spec.md#requirement-review-and-task-facts-retain-their-meaning) distinguishes substantive human review from automatic acceptance. Global calculations use platform rules instead of averaging incompatible local scores.

Apply the [broader-assessment contract](specs/worker-reputation/spec.md#requirement-broader-assessments-pool-source-evidence-under-scoped-rules) through the same calculation: project evidence for project reputation, pooled source evidence across the owning organization's projects for its assessment, and pooled eligible source evidence across organizations for global reputation. Use current organization defaults for the organization assessment with application-owned weights; changes refresh that assessment and future activations while frozen projects retain their configurations. Global settings remain platform-controlled. Do not require an established narrow assessment before its source observations can contribute, or average local percentages: ten/ten and thirty-six/forty correct answers pool to forty-six/fifty, or 92%, not 95%.

Apply each scope's eligibility, deduplication, comparison rules, cutoff, and window before its worker minima and rates. The initial broader count limit selects the most recent one hundred eligible observations per signal across the whole scope, not one hundred per project. Broader peer calculations must use source answers under their own comparison requirements rather than reuse a locally derived grade or windowed sample. Original source identities and times, correction guards, and known-answer precedence remain authoritative.

Retain the shared source-eligibility distinction: valid enabled keys supply evaluable known-answer grades, effective substantive reviews supply actual human verdicts, and eligible attempt outcomes supply reliability. Omitting those signals from a local score does not erase the source facts. Peer comparison additionally requires the source project's frozen agreement-scoring selection. Disabled source agreement supplies no scored peer evidence in any scope, protecting subjective preferences globally without a new classifier or eligibility-setting hierarchy. Reviewer-only agreement remains different from disabled scoring: comparisons can inform summaries while admission filters its own eligible contributors. This source-selection boundary does not let organization/project weights, worker minima, consensus thresholds, or windows reconfigure the global calculation. Global history is general work history, not certification for every task type.

Apply the [signal-role contract](specs/worker-reputation/spec.md#requirement-answer-quality-reliability-and-experience-have-distinct-roles) within those same scoped assessments: combine eligible correctness, human review, and peer agreement into answer quality, retain completion reliability separately, and expose experience as submitted answered-question counts. Only the three quality contributors enter the weight map or combined-quality evidence requirements. Separate reliability actions and permitted broader-history requirements reuse ordinary admission evaluation; no extra assessment lifecycle is needed.

Use the [experience contract](specs/worker-reputation/spec.md#requirement-experience-counts-submitted-answered-questions) to count authoritative answered QuestionResponses from successfully submitted attempts, once per question. Tasks can contain different numbers of questions: eight answered questions plus two skips supply eight experience observations and one completed reliability attempt. An all-skipped submission supplies the reliability completion but no question experience. Draft answers, unfinished work, and answers in returned/expired/cancelled attempts supply no experience. The task need not have reached its overall submission target; human-review status and corrections do not select or weight experience. Multiple answer parts or annotations remain one question, and retries do not duplicate it. Reuse original submission times, stable source identities, and each scope's existing history selection. Broader counts derive from pooled source answers rather than windowed project totals. With the initial one-hundred-observation window, experience describes up to one hundred recent eligible answered questions, with the window and supporting dates visible rather than implying a lifetime total. No experience points enter answer quality.

Use the [supplementary human-review contract](specs/worker-reputation/spec.md#requirement-human-review-is-supplementary-worker-evidence) through that explicit contributor set. Initial project, organization, and global defaults omit human review from combined quality; an organization can opt in through defaults or a draft override when individual review evidence is useful. Keep actual decisions and counts inspectable even when their scoring contribution is unselected. Do not infer passes from unreviewed answers, fill individual counts from a project sample, or silently remove an enabled contributor when it lacks evidence. Global selection remains platform-controlled and independent of local omissions. A minimum establishes whether a worker metric is usable; it creates no obligation to perform that many reviews.

Reviewing a representative project sample can investigate overall output quality and instruction problems, but cannot establish every worker's quality. Its rate describes the sampled responses, and a targeted queue of suspicious answers is not a representative estimate of all submissions. [Review sampling and budgets](../../future-features.md#review-sampling-and-budgets) belong to a separate review capability, including selection provenance. Consume actual effective human verdicts through the existing review boundary; this reputation change adds no sampler or budget allocator. Preserve automatic/manual acceptance and result visibility: choosing quality contributors does not make pending answers accepted, and automatic acceptance supplies no human quality evidence.

This keeps a worker's answer accuracy visible even when completion is inconsistent, and prevents volume of work from compensating for incorrect answers. The [reliability contract](specs/worker-reputation/spec.md#requirement-reliability-includes-unexcused-returns-and-excludes-legitimate-returns) defines its completion rate and exclusions. The [return-classification contract](specs/worker-reputation/spec.md#requirement-return-classifications-preserve-reasons-and-support-repair) protects legitimate and unreviewed returns while making confirmed unjustified returns count in reliability.

Extend the existing owner-authorized release action to capture the [structured return input](specs/task-allocation/spec.md#requirement-worker-returns-capture-reasons-without-waiting-for-classification) beside the authoritative attempt. `Attempt` currently accepts no release payload; add the deliberate input through the native Ash action/GraphQL boundary, retaining the post-lock deadline check and terminal outcome. Require an explicit single choice from the six shared preset reasons, nonblank custom text only for Other, and a separate optional comment for every choice, with each text field limited to one thousand characters independently. Use the shared reason codes from the input contract rather than deriving a classification from the label or adding organization-specific lists. Retain the selected code and both text fields separately from the reviewer's decision reason. Validate and capture them atomically with release, preserving original fields on terminal retries and historical reasonless attempts without inventing content. Classification must not hold release capacity while reviewers investigate. Every choice begins awaiting review, including time-limit and work-preference claims; only the authorized reviewer decision determines whether an eligible return contributes an unexcused reliability outcome. Retain attributable classification/correction history tied to that returned attempt, with an awaiting-review effective state until a reviewer decides. Keep it distinct from QuestionResponse accept/reject decisions and from the deferred worker dispute workflow; no general case-management system is needed.

Rebuild reliability from completed/expired/released source attempts and effective classifications. Return reasons are worker claims, and reviewers assess whether ordinary effort preference or a confirmed task defect explains the return. Raw return inspection and count breakdown include excused and unresolved events; the assessment's selected scoring sample remains separately identified. Classification changes use correction guards and the existing recalculation path across affected scopes. Each return retains its original identity and age, including after late classification or reinstatement.

Reuse `tasks.review` for scoped return inspection, classification, and correction, with active account/owning organization/membership checked on every operation and replay. Exclude the returning worker from deciding their own classification. Apply the existing [answer-review decision protocol](../../specs/task-review/spec.md#requirement-corrections-are-append-only-and-conflict-aware) through a separate attempt-linked return history: every decision has a nonblank reviewer explanation, actor, server creation time, and predecessor; the latest append is effective, and worker source fields remain immutable. A first decision expects no predecessor, while a correction expects the currently effective decision. Require a UUID request key scoped to attempt and requesting actor. After current authorization, recognize identical successful replays before checking their now-obsolete predecessor; return the original result without another append or changing a later effective decision. Changed content under the same key or a stale predecessor on a new request conflicts. Concurrent reviewers using the same prior state permit one valid save and require the other to refresh. Support retained released attempts, including completed/archived projects, without treating other terminal outcomes as returns or reopening collection. Worker reason/comment limits do not constrain reviewer explanations. Keep these protocol semantics explicit while resolving concrete guard storage and lock order with the publication/allocation design.

Apply the [original-outcome time contract](specs/worker-reputation/spec.md#requirement-reliability-history-uses-original-outcome-times) consistently across scopes: successful submission time for completions, lease deadline for eligible expirations, and release time for returns. Current `Attempt.terminal_at` supplies submitted/released transition times; `Attempt.deadline` supplies expiration age. The native expiry path records `terminal_at` when processing notices expiry, so do not use that processing time as reputation's event time or overwrite its source meaning. Count only authoritative eligible terminal outcomes captured in the snapshot, not live attempts inferred expired solely from the clock. Use original times for count ordering, time-window membership, supporting dates, and reinstatement cutoffs, with stable attempt identity for ties and deduplication. Classification or correction updates the same observation and reruns selection without making it newer. A return released one hundred days ago and confirmed unexcused today remains outside a ninety-day window, while the actual return and today's reviewer decision remain inspectable. The existing attempt facts provide these dates; no separate reputation event-time log is needed.

Use an explicit initial reliability minimum of twenty eligible task attempts in project, organization, and global assessments. Count the same C + E + U attempts used by the rate after each scope's cutoff and history selection, once per attempt; keep the default window at the most recent one hundred eligible outcomes. Eighteen completions plus one eligible expiration and one confirmed unexcused return establish 90% reliability, while eighteen completions plus two excused returns remain insufficient at eighteen. Excluded and unresolved outcomes stay visible without counting toward establishment. An unexcused-to-excused correction may reduce the selected count below the minimum; refresh the evidence state through the ordinary correction path rather than retaining the obsolete established rate. Reuse authorized organization defaults, draft-project overrides, and activation freezing for minimum overrides, with independent platform-controlled global settings. Smaller project histories may pool into established broader reliability. Reliability availability remains separate from combined answer quality and introduces no new automatic restriction rule.

Alternative rejected: penalizing all returns before investigation, or automatically excusing any return based on its chosen reason. The first would penalize legitimate task problems; the second would permit an unverified reason to bypass reliability. Reviewer classification keeps the distinction attributable while unresolved returns stay visible. Combining quality, reliability, and experience into one percentage, or averaging incompatible organization scores, would hide their different meanings.

### 2. Put known answers beside exact authored task contracts

A batch is represented by a Project and its authored Tasks, so no new Batch resource is needed. Bind typed keys to the [exact task/question/input contract](specs/worker-reputation/spec.md#requirement-known-answer-checks-bind-to-exact-task-evidence), using existing option/input identities and answer-family validation. Apply the [supported matching contract](specs/worker-reputation/spec.md#requirement-supported-answer-matching-uses-typed-values): canonical identity for single choice, complete unordered sets for multiple choice, complete ordered sequences for ranking, actual boolean values, and inclusive absolute numeric tolerance defaulting to zero. Do not add partial-credit selection/ranking scoring or silently interpret arbitrary strings or geometry. Validate expected values against the pinned question and exact authored input contract; numeric keys retain their own expected values/tolerances and correction history.

Reuse each applicable key to evaluate the eligible answers to that exact contract. Preparing a trusted reference once can support automatic grading across many workers without a human review of each submission. Ordinary task capacity still determines who encounters it; this is not a promise of per-worker checks. Boxes and segmentation require the separately specified [spatial-grading capability](../../future-features.md#spatial-grading-for-bounding-boxes-and-segmentation), not geometry interpreted by the reputation scorer.

Use ordinary allocation and the [activation feasibility checks](specs/projects/spec.md#requirement-activation-identifies-impossible-project-local-evidence-settings). Shared task capacity can be exhausted before later workers encounter known-answer questions. This avoids a second allocator or increased task demand; guaranteed per-worker delivery requires separate scope and is not supplied by the unfinished [qualification skeleton](../add-qualification-tests/proposal.md).

Enforce [key privacy](specs/worker-reputation/spec.md#requirement-keys-and-check-designations-remain-private) through scoped management actions and worker-facing GraphQL boundaries, including form/task/attempt traversal and mutation results. A hidden flag on a generally readable resource is insufficient. Authorized staff who also work follow the ordinary rules; no key-knowledge tracking is needed.

Retain key/matching-rule and enabled-state history for [correction and repair](specs/worker-reputation/spec.md#requirement-key-corrections-preserve-history-and-repair-assessments), using existing deliberate-action and retry conventions. Corrections preserve enabled status; explicit disabling/re-enabling uses the same history, publication guards, and recalculation path without a separate recovery lifecycle.

Build the two [organization reports](specs/worker-reputation/spec.md#requirement-organizations-can-inspect-known-answer-evidence-and-question-quality) as bounded read views over evaluation evidence. Worker reports reuse assessment-window selection; question reports aggregate all evaluable submissions for the exact task/question/input contract under one key revision through the report cutoff. Do not derive question diagnostics by summing workers' current assessment windows or add another configurable report window. Reuse key-change recalculation and label completed reports awaiting refresh. Use “known-answer evidence” and “question-quality reporting” in API descriptions, rather than unexplained “coverage” or “health” labels. A check is an expected-answer question within ordinary work; the reports add no worker interaction or separate test.

Alternative rejected: overwriting a key and losing the reason for earlier scores, or using a generic form-level answer key across different tasks.

### 3. Derive agreement only from comparable distinct peers

Group responses by exact task/question/pinned input contract and apply the [peer eligibility rules](specs/worker-reputation/spec.md#requirement-peer-comparison-requires-sufficient-comparable-evidence) and supported typed matching. Exact single-choice, complete-set multiple-choice, complete-order ranking, and boolean comparison share their semantics with known-answer grading. Numeric comparison uses the median of all eligible other answers, averaging the middle two for an even count, with the assessed scope's nonnegative absolute tolerance, initially zero. Preserve numeric/decimal precision and compare actual values rather than strings or rounded displays. Require the consensus fraction of all eligible peers to lie within the inclusive median-plus/minus-tolerance interval before judging the worker against that same interval. A key's tolerance remains independent, and the median is only a comparison center, not a generated answer key or collected canonical answer.

Peer eligibility uses valid answered QuestionResponses from successfully submitted attempts under the exact pinned contract, with one peer answer per distinct worker and the assessed worker excluded. Saved drafts, unsubmitted/unfinished outcomes, skips, and missing answers do not qualify. Review state does not select or weight peers: pending answers, system-accepted answers, and effective human accepts/rejects follow the same submission-based eligibility in project, organization, and global assessments. A manually rejected answer remains evidence of what that worker submitted, with its rejection retained separately for substantive human-review quality. A review-only decision or correction changes that worker's review-dependent assessment inputs, not the peer population, coverage, consensus, or other workers' peer grades. It does not require group-wide peer recalculation. Keep known-answer precedence, source-project agreement exclusions, completed-task eligibility, and the configured minimum/consensus rules; the same review-independent rule applies when assessing the worker's own submitted answer. This avoids letting uneven review sampling or reviewer-only judgments choose the voting population. Peer agreement measures consistency and can be high for a wrong answer; correctness and substantive review retain their stronger independent roles.

Scale the required other-worker count with the source task's frozen submission target T: `max(peer_floor, ceil(peer_coverage_fraction * (T - 1)))`. Initial settings in all three scopes use a floor of two, eighty-percent coverage, and a separate eighty-percent consensus threshold. Targets three/five/ten/thirty/three hundred therefore require two/four/eight/twenty-four/two hundred forty eligible other answers. Coverage uses requested other workers; consensus uses all eligible actual other answers after self/dedup/skip exclusions. Do not lower the coverage denominator for skips, sample only enough peers to pass consensus, or couple the two percentages. Organization/global comparisons use each source task's T and the assessed scope's own peer settings. Freeze project peer parameters with the rest of its configuration; current organization settings and platform global settings retain their approved ownership.

Under the initial defaults, two other workers must both agree; with eight eligible peers, six agreeing is insufficient while seven agreeing meets the consensus threshold. Nine eligible peers all participate, so seven out of nine cannot be made eligible by dropping one dissenting answer. Sparse/split comparisons supply neither scored successes nor failures nor worker minimum credit. Targets one/two cannot supply the floor, but ordinary submissions and other reputation evidence retain their meaning. Each exact answered question contributes at most one comparison for a worker regardless of peer-group size; the thirty-comparison worker minimum still establishes repeated evidence across questions.

Apply [known-answer precedence](specs/worker-reputation/spec.md#requirement-known-answer-grading-takes-precedence-over-peer-disagreement) before peer scoring to prevent double counting and contradictory penalties. Keep [unfinished comparisons](specs/worker-reputation/spec.md#requirement-unfinished-peer-comparisons-cannot-restrict-work) available as preliminary reviewer information without changing the existing submission target. A project with too few responses has no usable peer signal; the implementation must not create additional demand to manufacture one.

Alternative rejected: penalizing each deviation from the current plurality. The [repeated-disagreement contract](specs/worker-reputation/spec.md#requirement-repeated-disagreement-is-weaker-than-correctness) instead bounds influence below correctness and permits disabling agreement for subjective work.

For genuine preference collection, configure agreement out of quality scoring and enforcement; exclude that project's comparisons from scored peer evidence in all scopes and keep differing answers visible to authorized local reviewers. Human review should assess the published instructions and stated rubric, such as whether the requested explanation addresses the criteria, rather than agreement with the reviewer's taste. An organization's preferred opinion is not a trusted correctness reference. If there is no defensible selected quality evidence, preserve the unavailable/not-applicable result and separate reliability and experience instead of manufacturing quality from popularity or completion. This is guidance for configuring projects and conducting reviews, not a new automatic classifier of subjective questions or semantic grading system.

### 4. Freeze a small typed configuration at activation

Resolve direct organization defaults and draft-project overrides under the activation transaction, following the [project configuration contract](specs/projects/spec.md#requirement-organization-defaults-resolve-into-explicit-project-reputation-settings). Default edits and activation must serialize or obtain a coherent snapshot so activation cannot mix configurations.

Implement the [evidence feasibility checks](specs/projects/spec.md#requirement-activation-identifies-impossible-project-local-evidence-settings) as direct comparisons against the applicable history bound, local submission target, or authored check count. Return scoped validation errors or reviewer-only advisories without adding an allocation simulation or automatically changing settings. Broader entry rules use their own scope's limits.

Keep weights in one named application-owned definition and pass the effective map explicitly into the shared calculation. Developers should be able to change weights and focused tests in one place; avoid coefficients scattered across handlers, reports, jobs, and admission checks, or a database column per weight. The [weight contract](specs/worker-reputation/spec.md#requirement-application-owned-weights-are-explicit-calculation-inputs) specifies retained values, frozen projects, platform-weight recalculation, and the approved initial relative weights in all three scopes: correctness sixty, human review thirty, and peer agreement ten. Organization/global initial quality selects correctness and peer agreement with human review supplementary; each scope retains its own explicit effective settings rather than inheriting a source project's configuration.

Use the [normalized weighted average](specs/worker-reputation/spec.md#requirement-answer-quality-uses-a-normalized-weighted-average) over underlying success/count rates. Deliberately excluding human review normalizes the correctness/peer weights over seventy; it does not assign human review a zero. An enabled contributor below its minimum still makes the combined result unavailable. Keep display rounding outside the shared calculation and do not feed presentation percentages back into scoring. Default worker samples are twenty evaluated known answers, twenty substantive reviews when selected, and thirty eligible peer comparisons; the last is a worker history count, not the number of peers required for one question. These are starting product defaults with visible counts, not review quotas or statistical confidence guarantees. Resolve authorized minimum/window overrides through the existing project settings; keep weights application-owned.

Pass an explicit contributing-signal set into that same calculation for each result and retain the set with its provenance. Apply the [disabled/insufficient rules](specs/worker-reputation/spec.md#requirement-disabled-and-insufficient-signals-have-distinct-scoring-outcomes) to it. Filter organization/global per-signal inputs for project admission without changing their independent assessment or exposing private evidence. This implements [reviewer-only exclusion](specs/worker-reputation/spec.md#requirement-signal-actions-support-review-and-recoverable-project-suspension) without a separate scoring engine.

Use the existing assessment state and admission decision for the [initial-evidence path](specs/projects/spec.md#requirement-reputation-admission-provides-a-path-to-initial-project-evidence), rather than adding a qualification-attempt lifecycle. Requiring local history before any work would leave no way to earn it; established entry requirements instead use independently earned organization/global evidence.

Alternative rejected: making every setting global or exposing customer formulas. The bounded typed configuration gives organizations useful controls while keeping one application-owned algorithm; retained key history and calculation provenance do not require a generic policy/version hierarchy.

### 5. Add a new-work gate without changing ongoing authorization

Place the shared gate after account/organization/audience checks and committed allocation-retry resolution, before issuance. Preserve `WorkerEligibility` for existing-attempt authorization. Do not write `ProjectWorkerAccess` blocks for reputation: those blocks intentionally revoke ongoing access, unlike the [new-work-only contract](specs/task-allocation/spec.md#requirement-project-worker-eligibility-preserves-optional-membership).

Publish each scope's metrics, counts, provenance, and freshness together under the [fixed-snapshot contract](specs/worker-reputation/spec.md#requirement-assessments-publish-coherent-completed-results). Retain captured source revisions, evaluation cutoff, effective settings, and applicable reinstatement inputs. Project-local rule inputs after reinstatement belong to that same publication. Ordinary appends and passed refresh boundaries request follow-up; corrections, return-classification changes, key-state changes, settings changes, and reinstatement invalidate affected prepared results. Snapshot ordering must not regress the published source frontier or cutoff.

For each new issuance, evaluate frozen rules against the latest completed project/organization/global inputs actually required by that project. Reuse the shared signal selection, combination, minima, and threshold logic over those bounded metrics. The [fresh-admission contract](specs/worker-reputation/spec.md#requirement-new-work-evaluates-the-latest-completed-assessments) makes a previous denial history rather than a lasting barrier. Retain the outcome, reasons, and references to the actual inputs as scoped decision history, without copying source evidence or maintaining a second automatic-suspension state. A completed broader update needs no project-specific propagation job before the next request can use it.

The [pending-recalculation contract](specs/worker-reputation/spec.md#requirement-pending-recalculation-keeps-completed-assessment-inputs-usable) keeps each scope's last completed inputs usable, with as-of/pending metadata. One pending scope does not prevent use of newer completed inputs elsewhere. Apply [reinstatement cutoffs](specs/worker-reputation/spec.md#requirement-reinstatement-evaluates-selected-rules-using-subsequent-evidence) through shared history selection for selected local rules, preserving historical metrics and using the existing windows, minima, and thresholds. The admission evaluator applies the current reinstatement even when an older completed assessment predates it; that older evidence cannot restore a cleared rule while its replacement is pending.

Allocation currently locks Project, worker User, then task capacity. Coordinate publication in every consulted scope and reinstatement with issuance so the post-lock evaluation observes completed changes in a consistent transactional order. Organization/global publication must participate in this coordination even though it does not refresh project assessments. Submission/review callbacks already hold outcome/task locks and must not introduce inversions. The [atomic allocation contract](specs/task-allocation/spec.md#requirement-reputation-admission-is-atomic-and-shared-by-allocation-routes) owns the observable races and retry behavior.

Prepare any missing initial assessments before the allocation transaction and locks, after scoped authorization and committed-retry detection. Under the locks, revalidate authority, configuration, request key, latest completed inputs in all required scopes, and reinstatement; prefer concurrent completed assessments or conditionally publish the needed candidates. If a candidate is invalidated and its scope still lacks a completed assessment, release locks before re-preparing within the request. Only bounded admission comparisons and signal combination run under these locks; evidence scans, peer comparison, and full history calculations stay outside them. Follow the [first-access contract](specs/worker-reputation/spec.md#requirement-first-access-does-not-depend-on-a-queued-initial-calculation) without a queued warm-up lifecycle.

Keep history selection behind one small function accepting a window description and evaluation cutoff and returning observations plus any next time-dependent invalidation. The shared scorer receives those observations explicitly; it neither queries time nor filters its own window. Both time-based and count-only windows remain in scope. Apply the [time-window contract](specs/worker-reputation/spec.md#requirement-time-windows-expire-evidence-without-requiring-a-new-submission) and [count-window contract](specs/worker-reputation/spec.md#requirement-count-windows-select-recent-eligible-observations-per-signal), using original source identities for ties rather than correction/evaluation record identities. Recalculation consumes the returned freshness facts; admission consumes completed metrics and stays independent of window type.

Default new projects to the most recent one hundred eligible observations independently per signal, as specified by the [project defaults](specs/projects/spec.md#requirement-organization-defaults-resolve-into-explicit-project-reputation-settings). The explicit organization/global defaults use the same one-hundred limit and twenty/twenty/thirty worker minima under the broader-assessment contract, applying the limit after pooling. Selection also supplies the original oldest/newest observation times for each reported sample; retain these with the fixed-snapshot metrics so a recent calculation cutoff does not imply recent work. Count-window reputation survives inactivity until evidence or another calculation input changes. Optional time-based history starts at ninety days when that mode is selected without a duration override, using all eligible original-event observations in that interval and the existing evidence minima without an additional one-hundred-observation cap. Organization settings and draft-project overrides can adjust the positive duration; resolve and freeze the selected mode and its count or duration at activation, with independent platform-controlled global settings. Older source history remains retained, and too little remaining evidence becomes insufficient rather than fabricated success/failure. Keep the window types separate and preserve unchanged count-mode behavior. Numerical defaults are shared starting values, not configuration inheritance between scopes.

Use independent database connections and deliberate barriers for the concurrency checks in [tasks 4 and 5](tasks.md#4-recalculate-and-support-reviewer-recovery), including broader publication versus issuance, stale/corrected publication, activation races, and committed-retry recovery. A denied reputation evaluation must retain its decision history while creating no attempt or presentation.

Alternative rejected: caching an effective project decision that needs another background job after broader reputation improves. Fresh evaluation over completed metrics permits a worker to try again without scanning history on every request, waiting for jobs, or cancelling issued work.

### 6. Keep compensation commitments in Finance

Optional reputation-based pay bands and quality bonuses are approved. Organizations provide defaults and projects may override them; the future Finance activation contract resolves and freezes rate rules. A project can offer a standard rate and higher rates for sufficiently established project- or organization-scoped quality. Initial upgrades use known-answer correctness and substantive human review with minimum evidence. Peer agreement remains a monitoring and eligibility signal until its suitability for compensation has been established for that project. Competitor rates and thresholds are not QuickTrain defaults.

Historical reputation selects the rate for a future offer. A quality bonus evaluates performance on the offered work using criteria disclosed with that offer. Eligibility for better-paid projects is another use of reputation and does not imply a different price for identical work. Admission, answer acceptance, and monetary settlement are separate decisions.

Finance must show and freeze the quoted rate and bonus criteria when work is offered/fetched, with enough evidence to explain the selected band. It must reserve the maximum organization charge, including any promised conditional bonus, atomically with issuance. Later score/configuration changes affect future offers and cannot alter an issued offer's quoted rate or bonus rules. Skips, rejections, and partial answers remain task facts; the pinned rate terms determine payment treatment.

Reputation supplies scoped evidence and calculation provenance. Finance owns WorkOffers, funding reservations, settlement, ledger accounting, and payouts. This change adds no paid-offer or bonus tables and does not require a Finance implementation to complete. The future Finance change must restate these terms as behavioral specs and test rate changes, conditional bonus settlement, reservation failure, and offer/reputation races against the implemented reputation API.

Alternative rejected: retroactive rate reductions or adding a payment subsystem to make reputation useful. Frozen offers keep commitments predictable and let reputation ship independently.

### 7. Use scoped Ash operations and additive storage

Generate the Reputation domain/resources and migrations with the installed Ash tooling, then tailor them to the approved scope. Keep settings, keys/history, attempt-linked return reasons/classification history, completed assessments, scoped access-decision history, and manual reinstatement records distinct only where their lifecycles or authorization require it; do not create an additional automatic-suspension projection or generic policy-resource family. Use Ash UUID identities, explicit organization/project references, database constraints, and native actions/domain interfaces. No direct-Ecto exception is proposed.

Reuse the organization-capability path for management and review operations with explicit grants and fail-closed scope. Preserve external worker access through existing audience/attempt authority. Expose deliberate bounded GraphQL reads and mutations; authoring authority does not imply general read access. ### Future question capabilities

[Multiple acceptable known answers and question-level scoring controls](../../future-features.md) are recorded outside this change. Acceptable-answer sets belong to question/key authoring and grading; reputation will consume their grading outcome when implemented.

Question-level controls are approved future work requiring a published-question contract change. That work must also modify reputation's question selection, denominators and minimum-evidence counts, scoring and enforcement eligibility, explanations, and rebuild behavior. Resolve the controls through the pinned question version and effective project configuration, preserving already-active contracts. This release retains project-level settings; for a form mixing factual and subjective questions, disable agreement scoring/enforcement for the whole project until selective controls exist rather than treating every question as objective. No question schema or extra override hierarchy is introduced here.

[Spatial grading](../../future-features.md#spatial-grading-for-bounding-boxes-and-segmentation) will define type-appropriate comparisons for reference annotations and peers. Reputation should consume supported grading/comparison outcomes through the existing eligibility, provenance, minimum-evidence, and correction boundaries; it should not own box/mask geometry or acquire a generic grader plugin framework in advance. Semantic free-text grading remains separately out of scope. [Review sampling](../../future-features.md#review-sampling-and-budgets) must preserve worker-specific evidence and distinguish routine samples from targeted investigations without changing reputation's source ownership.

Spatial partial credit is approved future work. Its future change must extend the grading inputs, quality aggregation, reports, and scoped pooling to preserve fractional credit, distinguishing earned credit from actual evaluated-question counts and retaining correction provenance. Do not count multiple objects in one question as extra worker observations or round partial grades into fabricated full successes/failures. The [future spatial-grading feature](../../future-features.md#spatial-grading-for-bounding-boxes-and-segmentation) records the approved bounding-box object-count formula: correct matches divided by correct matches plus missed references plus extra annotations, using one-to-one same-label matches meeting the project's configurable minimum IoU. Choose the pairing with the most qualifying matches, then the highest total IoU, with a deterministic final tie-break independent of annotation order. Apply the same pairing rule to separately outlined segmentation objects; duplicates and other unmatched submitted annotations remain extras. Qualifying objects earn full object credit; partial question credit comes from the object-count formula, not a second continuous IoU multiplier. The approved per-object IoU starting minimum is 70% for both bounding boxes and separately outlined segmentation objects, comparing actual regions/pixels for the latter. Keep it project-adjustable and preserve it through the future capability's frozen active-project contract; validate its suitability against representative annotations, including small objects. Average eligible fractional grades equally per evaluated question after the existing minimum, including when pooling across projects; a wrong label contributes both a missed reference and an extra annotation.

Separately outlined segmentation objects use the same approved object-count calculation, with IoU over polygon regions or mask pixels. Category-based segmentation uses the arithmetic mean of continuous per-category pixel IoU for categories present in either answer, excluding categories absent from both and unlabeled background; missed or incorrectly added categories score zero. Reputation consumes the resulting question grade and counts one evaluated question, regardless of the number of categories or pixels. Across all three spatial styles, a trusted explicitly empty reference and a worker's submitted valid empty annotation earns full credit and one evaluated question; an explicit empty annotation on only one side earns zero. Skipped, missing, untouched, or unfinished answers remain unscored, and absence of a reference never means an empty expected answer. The future question contract must preserve this distinction.

Spatial peer comparison retains all actual submitted other-worker answers tied for the greatest mean question-score similarity to the other eligible peers, excluding each candidate's self-comparison. Exclude the assessed worker before selecting representatives or establishing consensus; do not use worker reputation to select or weight peers. Retain completed-task eligibility, scoped coverage and consensus settings, the all-eligible-peer denominator, source-project agreement exclusions, known-answer precedence, and the repeated-worker-evidence minimum. Each representative supplies its ordinary peer vote, not an extra vote. Detect exact ties using unrounded means, check full-pool consensus independently around every retained representative, and leave the question unscored if any fails that condition. Otherwise, average the assessed worker's actual fractional comparison grades against every tied representative into one question observation. A unique best answer is the one-representative case. Calculable representatives alone establish neither consensus nor a trusted/canonical collected answer. No geometry synthesis or submission/export rewriting is introduced.

The approved initial whole-answer peer similarity cutoff is 80% in all three assessment scopes, independently configurable through organization defaults/project overrides and platform-controlled global settings. Project activation freezes its cutoff; broader assessments use their own effective cutoff rather than a source project's override. Count a peer toward consensus around each representative when its actual spatial question comparison score meets the cutoff inclusively, without rounding; this is separate from the 70% starting individual-object IoU rule and from the fraction of all eligible peers required for consensus. Once consensus is established around every retained representative, preserve the assessed worker's actual fractional grade even when it is below the similarity cutoff. Detailed annotation contracts including the object-pairing final tie-break remain undecided. The current non-spatial matching, binary success/count calculations, relative weights, and minima stay as approved; no spatial grading implementation or speculative generic grader is introduced here.

## Risks / Trade-offs

- **[Majority agreement can reward conformity]** → Exclude ambiguous comparisons, require sufficient distinct peers and worker history, bound agreement below correctness, and default enforcement to reviewer information.
- **[Unreviewed returns accumulate]** → Keep total counts, worker reasons, and classification breakdown visible for reviewer investigation; do not turn frequency alone into a reliability failure or add a timed review-expiry penalty.
- **[Per-worker human-review quotas grow with workforce size]** → Omit human review from default combined quality and reuse applicable reference keys; keep actual review evidence supplementary. Future project-budget sampling provides project diagnostics without inventing individual quality or per-worker review coverage.
- **[Faulty keys or small samples misclassify workers]** → Preserve insufficient-evidence states, counts, key history, broad-failure evidence, and correction/reinstatement workflows.
- **[Workers encounter too few known-answer questions]** → Validate structurally impossible local minima, advise managers that ordinary allocation does not guarantee delivery, and expose actual evidence counts without treating missing evidence as failure.
- **[Correct answers conflict with peers]** → Use known-answer grades for designated checks and keep their peer disagreement diagnostic-only, including after key disabling.
- **[Late peer answers change earlier comparisons]** → Keep unfinished comparisons preliminary and out of scores/enforcement; evaluate only after the task reaches its target, without adding collection demand.
- **[A window expires while a worker is inactive]** → Track the next invalidation, schedule repair, and let reads detect missed refreshes without pausing access or waiting for a new submission.
- **[Count-window reputation can reflect old work]** → Preserve the approved behavior through inactivity, show the original oldest/newest supporting observation times separately from the calculation cutoff, and retain configurable time-based windows.
- **[Source corrections race admission or recalculation]** → Mark affected calculations for refresh, prevent obsolete publication, and order completed restriction changes with issuance under database locks.
- **[Recalculation is delayed]** → Accept that an allowed worker may receive more tasks before a new restriction takes effect, or an existing restriction may last until repair/reinstatement. Keep pending updates visible and retry failed jobs; never convert that delay into a new worker pause.
- **[An earlier denial outlives improved reputation]** → Reevaluate each new request using the latest completed inputs and retain prior outcomes only as history. Record the exact assessment references and reinstatement used for every decision.
- **[New workers cannot earn required local history]** → Permit project-local participation with insufficient evidence; use independently earned organization/global evidence for established-history entry requirements.
- **[Scoring and enforcement become a generic rules system]** → Keep a bounded configuration and application-owned algorithm; add only lifecycle-specific resources.
- **[Global scores combine incompatible local assumptions]** → Pool eligible source evidence under platform rules instead of averaging local scores; exclude a source project's disabled peer comparisons in every scope and keep private organization evidence inaccessible. Global history does not certify every task-specific skill.
- **[Future pay changes surprise workers]** → Keep quoted rate and bonus rules in immutable funded Finance offers; apply later changes to future work.
