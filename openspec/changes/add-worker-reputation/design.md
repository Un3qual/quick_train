## Context

See [proposal.md](proposal.md) for scope. This change owns the reputation decisions approved on 2026-10-05 and previously placed in `record-future-product-architecture`. It is an implementation proposal, not evidence that reputation has shipped. The approved compensation direction is retained below as a future Finance integration contract.

Core collection already supplies immutable TaskInputs, submitted QuestionResponses, attempt provenance, append-only ReviewDecisions, frozen Projects, and sealed exports. `QuickTrain.Tasks.Reviews.QuestionReview.initial_decisions!/2` automatically accepts answered submissions, so acceptance alone is not correctness evidence. `QuickTrain.Tasks.Access.WorkerEligibility` currently serves both allocation and existing-attempt authorization; putting reputation restrictions directly into that shared filter would revoke work already issued. `AttemptAllocation` also replays allocation request keys before selecting new work. These are concrete integration boundaries for this change.

The [worker-reputation delta](specs/worker-reputation/spec.md) defines the new behavior; [projects](specs/projects/spec.md) and [task-allocation](specs/task-allocation/spec.md) extend the implemented collection contract. This change does not depend on media execution or Finance.

Keep [organization staff and workers separate](specs/task-allocation/spec.md#requirement-organization-staff-and-worker-participation-remain-separate) globally: effective management, authoring, review or assignment authority in any organization excludes worker participation in every organization, including open-external and explicit-allow routes. Ordinary membership alone remains compatible with internal work. Use one shared Ash `NotStaff` check derived from current effective grants, rather than a global account type, persona resource, cached session flag or reputation setting. Permission changes must preserve original evidence ownership. Retain the small native self-review checks and require a distinct reinstating actor for decisions about earlier work.

Implement `NotStaff` as a reusable Ash policy check using a native existence query over effective RoleAssignments and the centrally defined application staff capabilities. The current product capabilities are `projects.manage`, `forms.manage`, `datasets.manage`, `dataset_imports.manage`, `assets.manage`, `tasks.review` and `tasks.assign`; adding a management/authoring capability must update this one definition. Reuse the existing active-account/organization/membership grant predicate without filtering to the work's organization. A missing actor or failed authority lookup denies worker participation. Role names, ordinary membership and read-only grants do not designate staff. This global exclusion grants no cross-organization staff access; management/review actions retain their scoped policies.

Require `NotStaff` in addition to existing audience/ownership policies on worker fetch, protected worker reads, start, answer save and submission, including committed-allocation retries and existing live attempts. Recheck after existing authorization waits. For direct assignment, apply the same predicate to the target worker; the staff caller still needs scoped `tasks.assign` and must not be rejected for performing the assignment. Subsequent worker operations after a committed staff grant fail through these ordinary policies; add no grant-rejection workflow, cancellation sweep or role-transition resource. Keep owner release available through the existing release action under its ordinary account, audience, ownership and state checks, exempting only the staff exclusion for this cleanup. It returns no protected work content, allows no answer changes/submission and creates no quality/experience credit; ordinary return/expiration classification rules remain effective. Add no new cleanup API or workflow. Keep historical records and previously submitted grading unchanged.

The specs own behavioral requirements and scenarios. This design records approved implementation choices, rationale, and verification boundaries; the [tasks](tasks.md) link those contracts to delivery work.

## Goals / Non-Goals

**Goals:**

- Keep authoritative evidence in its owning domain and make assessments reproducible, scoped, and explainable.
- Implement known-answer checks and conservative peer comparison using existing immutable task identities and typed answers.
- Make project restrictions recoverable without coupling them to account bans, answer acceptance, or payment.
- Use Ash resources, actions, relationships, policies, constraints, and generators; use existing Oban infrastructure for recalculation where asynchronous work is appropriate.

**Non-Goals:**

Follow the [proposal's scope exclusions](proposal.md#what-changes). In particular, do not add a general policy engine, duplicate evidence stream, separate automatic-suspension projection, or speculative Finance adapter/plugin interface.

## Decisions

### Lifetime and EWMA reputation

Provide equal-weight lifetime and observation-based EWMA performance alongside the separate all-history experience count under the [view](specs/worker-reputation/spec.md#requirement-lifetime-and-ewma-preserve-distinct-performance-views), [evidence](specs/worker-reputation/spec.md#requirement-evidence-minimums-account-for-ewma-weight-concentration) and [rule-basis](specs/worker-reputation/spec.md#requirement-performance-rules-select-one-explicit-history-basis) contracts. Use one half-life per scope and independent eligible ordering per signal. Numerical defaults, normalized finite-history formulas and feasibility examples belong to those specs. Lifetime and EWMA are two results in one completed assessment, not separate heads, source stores or job lifecycles.

The selected model replaces hard count/time windows and their time-expiry scheduling. A single decay parameter gives gradual recency weighting without several overlapping periods or an invented prior. The [normalized finite-history EWMA definition](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.ewm.html) provides the mathematical reference; this introduces no pandas/runtime dependency. Its evidence size measures weight concentration rather than a confidence guarantee. The defaults remain product starting values, not measured optimal parameters.

The [starting quality and reliability threshold scenarios](specs/worker-reputation/spec.md#requirement-configured-rules-have-explicit-starting-thresholds) calibrate tolerance for an isolated eligible failure near the initial evidence minimum while identifying a recent failure streak. Quality calibration retains the known-answer and selected substantive human-review thresholds; peer agreement retains its lower threshold because agreement is weaker evidence of correctness. Keep the shared half-life and ordinary outcome weights; add no first-failure exception or separate grace counter. Resolve selection and action defaults together under the [project settings contract](specs/projects/spec.md#requirement-organization-defaults-resolve-into-explicit-project-reputation-settings): correctness and peer agreement supply combined reviewer quality, reliability is separate, human-review scoring is unselected, and experience is reportable. Enabled signals and combined quality initially inform reviewers; selecting human review without an action override also remains informational. Require an explicit automatic rule in organization defaults or draft overrides before freezing project enforcement. Thresholds alone enable no action or broader entry requirement.

Verify the defaults using two complementary checks during implementation. ExUnit unit tests prove the scorer's formulas, evidence boundaries and recovery; integration tests prove that native submissions, effective reviews and key repairs supply the correct inputs. A bounded set of representative typed answers and chronological worker histories records independently judged acceptable/unacceptable outcomes, then checks whether the configured scores raise sensible concerns. Include occasional mistakes, sustained incorrect work, inadequate evidence, excluded preference questions, minority-but-correct answers and faulty-key repair. Retain any mismatch and its rationale so it prompts review of the check, instructions or central defaults rather than an unexplained expected-value update. Passing arithmetic or synthetic cases is not empirical validation of the defaults for every task type.

These are development/release verification checks before enabling optional automatic enforcement, not a per-organization calibration requirement, worker review quota, calibration status field or additional admission gate. When representative real submissions become available, inspect a small pilot for instruction clarity and false/missed concerns; preserve what evidence was actually available instead of claiming a real-world pilot from synthetic fixtures. Any proposed default changes must be reconciled with the approved specs and frozen-project behavior. Keep one shared scorer and existing report/repair paths; add no calibration service or parameter-search framework.

Recovery follows those same weights and thresholds as newer eligible outcomes arrive. The worked recovery count is illustrative, not a quota, counter or waiting period. Reviewer-only rules permit continued work; authorized reinstatement of a selected project-local automatic rule uses its existing subsequent-evidence contract while historical performance retains earlier failures.

Correctness histories assume eligible known-answer evaluations, clear instructions and trustworthy typed references, except the faulty-key case which deliberately starts with an incorrect reference; return cases use eligible terminal attempts and attributable reviewer classifications. Peer cases assume completed tasks and sufficient eligible distinct-worker group answers, including the assessed worker; question participation and known-answer precedence still apply. These are synthetic development fixtures, not empirical claims about every task type. Keep other metrics and independently configured entry requirements separate.

### 1. Separate evidence dimensions and assessment scope

Add `QuickTrain.Reputation` for derived assessments and their evaluation workflows. Keep the global User and authoritative Attempts, QuestionResponses and ReviewDecisions in their existing domains, retaining source references rather than a parallel event store. The [assessment contract](specs/worker-reputation/spec.md#requirement-scoped-assessments-preserve-evidence-and-uncertainty) owns metric/evidence states and the independent freshness metadata.

Use one source-selection and calculation path for the [three scopes](specs/worker-reputation/spec.md#requirement-broader-assessments-pool-source-evidence-under-scoped-rules). Change worker/organization/project filters and supply that scope's effective settings; establish eligibility after pooling, calculate both lifetime and EWMA performance, and aggregate all-history experience through the same captured cutoff. Do not combine narrower percentages, samples or decay ranks. Current organization settings and platform-controlled global settings remain independent of frozen Project settings. Retain original source identities/times and revision provenance with completed results.

Query eligible known-answer, human-review and reliability facts independently of whether a narrower score selects them. Peer queries additionally filter on the source Project's frozen agreement-scoring selection and the pinned question's participation boolean, so project/question exclusions survive broader pooling. This is one shared source predicate, not another setting hierarchy. Keep reviewer-only admission selection separate from disabled source scoring. The [signal roles](specs/worker-reputation/spec.md#requirement-answer-quality-reliability-and-experience-have-distinct-roles) and [experience counting](specs/worker-reputation/spec.md#requirement-experience-counts-submitted-answered-questions) remain separate inputs to the shared scorer; no overall weighted reliability/experience score is stored.

Consume effective substantive human verdicts through the existing review boundary under the [supplementary-review contract](specs/worker-reputation/spec.md#requirement-human-review-is-supplementary-worker-evidence). Automatic initial acceptance is a collection fact, not human quality evidence. A project sample describes its reviewed answers and cannot be copied into unreviewed workers' counts. [Review sampling and budgets](../../future-features.md#review-sampling-and-budgets) supply a future workflow and provenance, not another scorer; this change consumes actual review decisions without creating a sampler or quotas.

Extend the native owner-authorized return action with the [three worker reason fields](specs/task-allocation/spec.md#requirement-worker-returns-capture-reasons-without-waiting-for-classification), retaining post-lock deadline checks and cleanup-only return access after a staff grant. The [supporting collection change](../simplify-work-participation-and-processing/design.md) owns TaskParticipation naming, reduced states, reservations and implicit acceptance. Use one append-only participation-outcome decision resource, `ReliabilityDecision`, for returned or expired outcomes, not separate return and expiration workflows. Reuse the scoped review UUID/predecessor pattern, attributable explanations, current tasks.review checks and self-review exclusions. Native terminal state remains returned or expired; classification never revives work. Expirations have no fabricated worker return reason. Unstarted direct assignments remain neutral even if classified unexcused.

Rebuild [reliability](specs/worker-reputation/spec.md#requirement-reliability-includes-unexcused-returns-and-excludes-legitimate-returns) from successful submissions and eligible reviewer-confirmed unexcused returned/expired participations. Returned and expired outcomes are initially awaiting review and neutral; expiry frees capacity without establishing fault or requesting a score refresh. Use native terminal_at for submitted/returned observations and immutable deadline for expiration, retaining both original and processing/decision times. Classification changes from neutral to unexcused or back repair the original observation rather than append a new one; neutral-to-neutral/explanation-only changes add no refresh. Unstarted assignments and cancellations are excluded. Keep C/(C+E+U), separate lifetime/EWMA minima, informational outcome breakdowns and no effect on answer quality.

Alternative rejected: combining correctness, completion and experience into one percentage, averaging incompatible local scores, or inferring return validity from worker claims/frequency. Independent source dimensions and attributable classification make the result explainable without another event ledger.

For [informational task/project counts](specs/worker-reputation/spec.md#requirement-evidence-counts-include-informational-task-and-project-coverage), retain two scalar counts per reported metric on the completed assessment. Deduplicate native Task and Project identities from that metric's eligible sample, including failures; compute them once after final eligibility, not on each reviewer row. Lifetime and EWMA share these unweighted counts because they use the same observations. Any exposed selected-rule post-reinstatement counts use that rule's filtered sample. These fields do not enter the scorer, minimums, admission or Finance criteria and do not imply skill certification or independent observations.

Use native distinct-count aggregates for experience alongside its existing total/date aggregates, without materializing every answer solely for these counts. Human-review and reliability counts can use equivalent aggregates in the same read snapshot; correctness/peer counts follow the application's final matching eligibility over captured lightweight inputs. Return the saved scalars through existing list/detail paths, leaving missing-assessment counts unavailable. Global responses disclose only the aggregate values, with no source identities or project/organization names. Add no coverage resource, customer settings, source ledger or report job.

### 2. Put known answers beside exact authored task contracts

A batch is represented by a Project and its authored Tasks, so no new Batch resource is needed. Bind typed keys to the [exact task/question/input contract](specs/worker-reputation/spec.md#requirement-known-answer-checks-bind-to-exact-task-evidence), using existing option/input identities and the [shared typed matching contract](specs/worker-reputation/spec.md#requirement-supported-answer-matching-uses-typed-values). Implement key creation through the [authoring lifecycle](specs/worker-reputation/spec.md#requirement-known-answer-authoring-respects-the-project-lifecycle): take the existing Project lock before checking draft state and task ownership, validate expected values against the authored contract, and serialize with activation/removal. Activation revalidates keys and freezes check designations. Retained keys protect their exact task references; reject removal of a keyed draft Task explicitly before native deletion rather than rely on an opaque foreign-key error or create a deletion/archive lifecycle.

Reuse each applicable key to evaluate the eligible answers to that exact contract. Preparing a trusted reference once can support automatic grading across many workers without a human review of each submission. Ordinary task capacity still determines who encounters it; this is not a promise of per-worker checks. Boxes and segmentation require the separately specified [spatial-grading capability](../../future-features.md#spatial-grading-for-bounding-boxes-and-segmentation), not geometry interpreted by the reputation scorer.

Use ordinary allocation and the [activation feasibility checks](specs/projects/spec.md#requirement-activation-identifies-impossible-project-local-evidence-settings). Shared task capacity can be exhausted before later workers encounter known-answer questions. This avoids a second allocator or increased task demand; guaranteed per-worker delivery requires separate scope and is not supplied by the unfinished [qualification skeleton](../add-qualification-tests/proposal.md).

Enforce [key privacy](specs/worker-reputation/spec.md#requirement-keys-and-check-designations-remain-private) through scoped management actions and worker-facing GraphQL boundaries, including form/task/attempt traversal and mutation results. A hidden flag on a generally readable resource is insufficient. Organization staff cannot work in any organization under the shared `NotStaff` boundary; retain ordinary grading of earlier submissions when permissions change, without key-knowledge tracking or an authorship-based scoring exception.

Use key-specific current/revision records and scoped Ash actions for the [correction protocol](specs/worker-reputation/spec.md#requirement-key-corrections-preserve-history-and-repair-assessments), following native append-only review conventions. Retain actor, request content and expected predecessor for authorized replay/conflict checks. The technical integration table defines owner locks, affected-worker discovery and atomic refresh writes. Keep this lifecycle separate from reliability classification decisions without introducing a generic correction engine or key-recovery state.

Keep worker assessment reports and exact-question diagnostics on the separate [reviewer read paths](#reviewer-read-paths). Reusing completed worker results and calculating uncached question diagnostics avoids a second report-publication lifecycle. API descriptions use “known-answer evidence” and “question-quality reporting” rather than unexplained check terminology.

Alternative rejected: overwriting a key and losing the reason for earlier scores, or using a generic form-level answer key across different tasks.

### 3. Derive agreement only from comparable distinct peers

Select answers by exact task/question/pinned input contract and use the [shared typed matcher](specs/worker-reputation/spec.md#requirement-supported-answer-matching-uses-typed-values) for known-answer and peer comparisons with [bounded answer processing](#bounded-answer-processing). Preserve numeric precision through median/concentration calculation and binary matching. Key tolerance is retained per key in every scope. Project peer tolerance is a separate frozen input resolved from project defaults/draft overrides; organization/global peer tolerance is fixed at zero. Nonzero broader tolerance overrides are rejected, and a project-default tolerance cannot configure the organization assessment. One project tolerance can suit consistent numeric units/scales; authoring guidance recommends zero for mixed scales without introducing a unit detector or normalization scheme. Question-specific peer tolerances remain future question-contract work. The specs own family semantics, numerical defaults and boundary examples; do not add a separately maintained database grader or geometry interpretation.

Add one boolean attribute to the native Forms Question for [peer participation](specs/versioned-forms/spec.md#requirement-questions-declare-peer-reputation-participation), default true. Reuse scoped `forms.manage` authoring, existing FormVersion mutation/publication locking, native copy and GraphQL inspection; copy the value and freeze it with publication. Read it through each source project's pinned FormVersion. Apply [exclusions](specs/worker-reputation/spec.md#requirement-question-exclusions-apply-before-peer-reputation-scoring) before peer grouping, count/rank calculation and broader pooling; keep known-answer, review, experience and attempt reliability eligibility independent. A false value adds no settings hierarchy, separate resource or mutable active-project override. Reports explain exclusions through the retained source contract; no new evidence state or question-report cache is required.

Select [eligible peers](specs/worker-reputation/spec.md#requirement-peer-comparison-requires-sufficient-comparable-evidence) from submitted answered TaskParticipations, deduplicated by worker. Use one inclusive group reference, including each assessed worker's own single vote, under the scope's settings for every group size. Coverage is max(F, ceil(P*T)) over the whole source target, initially F=3 and P=0.8, separate from eighty-percent consensus and the thirty-comparison worker minimum. Neither peer eligibility nor vote weight depends on review verdict. Review-only changes refresh that worker's human-review inputs without peer fan-out. Completed-task and known-answer precedence rules remain effective. Reuse common group results within the bounded calculation/discovery execution where practical; add no persistent peer cache or N separate leave-one-out references.

Apply [known-answer precedence](specs/worker-reputation/spec.md#requirement-known-answer-grading-takes-precedence-over-peer-disagreement) before peer selection. Query check designation independently of enabled-key grading so disabling a key does not turn its question into peer evidence. [Unfinished comparisons](specs/worker-reputation/spec.md#requirement-unfinished-peer-comparisons-cannot-restrict-work) remain scoped diagnostics, separate from pending calculation metadata and scored observations. Ordinary task capacity remains authoritative; reputation cannot create additional demand to complete a comparison.

Alternative rejected: grading unfinished or weakly split groups against the current plurality, choosing or weighting peers by reputation, or using reviewer verdicts to select voters. The [repeated-disagreement safeguards](specs/worker-reputation/spec.md#requirement-repeated-disagreement-is-weaker-than-correctness) retain independent correctness evidence. Mixed factual/preference forms use the simple question exclusion; whole-project agreement exclusion remains available. No automatic subjective classifier, per-project question override or customer question-weight formula is introduced.

### Warn about low reference-match rates and repair global source selection

Under the [low reference-match warning contract](specs/worker-reputation/spec.md#requirement-question-diagnostics-warn-about-low-reference-match-rates), reuse coherent on-demand exact-question key-match counts. Before target T is reached, at least three evaluated distinct workers and at most twenty percent matches produce a clearly labeled preliminary warning with evaluated/requested counts. After target completion, the completed-sample warning additionally requires max(3, ceil(0.8*T)) evaluated workers. Skips never lower T; failure of completed coverage cannot be hidden by carrying forward a preliminary label. One central application definition owns these thresholds independently of peer/admission settings. Both stages require the ordinary private tasks.review path and captured key/cutoff; neither adds a job, persisted warning lifecycle, automatic key edit, worker failure or pause.

Derive the warning from the existing counts with one small pure predicate, not another peer-comparison or clustering pass. Use the key's own typed matching/tolerance; numeric peer tolerance and median calculations do not participate. Dispersed failures can warn just as consistently matching alternatives can. Worker evidence minima, EWMA, reinstatement, peer-scoring selection and question peer exclusion do not suppress an enabled-key diagnostic. Organization applications surface "Low reference-match rate—review this question" to their own authorized reviewers with counts, captured key revision/cutoff and available answer patterns. The label identifies a low match rate, not established worker inaccuracy or proof of a faulty key. Existing manager correction/disabling automatically propagates through repair jobs; diagnostic reads remain read-only. Add no notification service, recurring vetting process, trusted-organization registry or concern lifecycle. The separate organization reporting change owns additional categorical answer-pattern summaries; warning calculation does not depend on their availability.

Represent exceptional global exclusions as explicit typed key/project source selections in the existing platform-controlled global settings. A key selection excludes its correctness grades; a project selection excludes its quality/reliability observations. Apply them in global source queries before counts and lifetime/EWMA ranking, leave local queries and all-history experience unchanged, and preserve check designation so exclusion cannot create peer fallback. Retain the effective selections and attributable maintenance reason with calculation provenance. Permit only the private trusted server operator command to exclude or explicitly restore sources or change global settings; ordinary key repair cannot clear that selection. Use internal Ash operations, active User attribution, a nonblank reason and expected global settings revision under the spec's fail-closed maintenance boundary. Do not expose a GraphQL mutation, user-supplied operator flag or new platform-role hierarchy. Keep existing revision guards and atomic durable refresh writes; no separate maintenance ledger, retry coordinator or dependency on deferred operator onboarding is needed.

Reuse the settings revision, capture/publication guards and durable revision-specific global settings refresh job for exclusion/restoration. This avoids another trust service, recalculation path or worker access state. Original records and prior completed results remain available under existing privacy rules. Missing remaining evidence still has its ordinary meaning for an explicitly configured global entry rule; a source exclusion is not a fabricated passing score or automatic worker reinstatement.

Alternatives rejected: requiring consensus before showing a low reference-match warning, or automatically deciding key truth/invalidating sources because many answers fail the key. A warning can identify a bad reference, unclear instructions, difficult work or poor worker performance; reviewers investigate the cause. Existing known-answer grading continues until authorized correction/disabling. Keep consensus safeguards unchanged for scored worker peer agreement. Global metrics remain informational by default, with automatic project entry requiring explicit opt-in.

### 4. Freeze a small typed configuration at activation

Resolve direct organization defaults and draft-project overrides under the activation transaction, following the [project configuration contract](specs/projects/spec.md#requirement-organization-defaults-resolve-into-explicit-project-reputation-settings). Default edits and activation must serialize or obtain a coherent snapshot so activation cannot mix configurations.

Implement the [evidence feasibility checks](specs/projects/spec.md#requirement-activation-identifies-impossible-project-local-evidence-settings) as direct comparisons against the declared scope's history bound, per-question peer capacity and authored per-worker source maxima. Derive the local maxima with native Ash counts of Tasks and eligible task/question contracts; exclude designated checks from the peer maximum even when disabled, and exclude questions whose pinned participation boolean is false. The existing one-attempt-per-worker/task contract supplies the finite bound without simulating allocation or predicting shared-capacity delivery. Return scoped errors for impossible automatic inputs and advisories for reviewer-only limits. Broader entry rules use their own scope's limits.

Keep weights in one named application-owned definition and pass the effective map explicitly into the shared calculation. Retain resolved values on frozen Projects and in completed assessment provenance under the [weight contract](specs/worker-reputation/spec.md#requirement-application-owned-weights-are-explicit-calculation-inputs). Developers adjust one central definition and its focused tests; avoid coefficients scattered across handlers, reports, jobs and admission, or a database column per weight. Organization/global assessments keep independent explicit settings rather than inherit a source project's configuration.

Use one shared pure calculation for the [normalized weighted average](specs/worker-reputation/spec.md#requirement-answer-quality-uses-a-normalized-weighted-average), explicit contributing signals and their [evidence states](specs/worker-reputation/spec.md#requirement-disabled-and-insufficient-signals-have-distinct-scoring-outcomes). Supply underlying rates/counts and retained effective weights; keep display rounding outside the scorer. The specs own starting numerical defaults, selection/minimum behavior and boundary examples; those defaults are evidence requirements, not review quotas or statistical confidence guarantees.

Pass an explicit contributing-signal set into that same calculation for each result and retain the set with its provenance. Apply the [disabled/insufficient rules](specs/worker-reputation/spec.md#requirement-disabled-and-insufficient-signals-have-distinct-scoring-outcomes) to it. Filter organization/global per-signal inputs for project admission without changing their independent assessment or exposing private evidence. This implements [reviewer-only exclusion](specs/worker-reputation/spec.md#requirement-signal-actions-support-review-and-recoverable-project-suspension) without a separate scoring engine.

Use the existing assessment state and admission decision for the [initial-evidence path](specs/projects/spec.md#requirement-reputation-admission-provides-a-path-to-initial-project-evidence), rather than adding a qualification-attempt lifecycle. Requiring local history before any work would leave no way to earn it; established entry requirements instead use independently earned organization/global evidence.

Alternative rejected: making every setting global or exposing customer formulas. The bounded typed configuration gives organizations useful controls while keeping one application-owned algorithm; retained key history and calculation provenance do not require a generic policy/version hierarchy.

### 5. Add a new-work gate without changing ongoing authorization

Keep reputation in the shared new-issuance gate after ordinary authorization and committed-retry resolution. Preserve `WorkerEligibility` for existing-attempt authorization and keep reputation out of `ProjectWorkerAccess` blocks, which revoke ongoing access. ### 6. Keep compensation commitments in Finance

Optional reputation-based pay bands and quality bonuses are approved. Alternative rejected: retroactive rate reductions or adding a payment subsystem to make reputation useful. Frozen offers keep commitments predictable and let reputation ship independently.

##### Bounded answer processing

For one worker's small Task, load its question definitions and draft outcomes together as ordinary native reads and validate/submit the Task atomically. Do not introduce per-question processing jobs, checkpoints or resumable submission stages. Public Relay pagination and bounded typed-child/source traversal remain unchanged; few question definitions do not bound the size of one answer, a peer group or a complete worker history. The following paging rules apply to those growing bulk evidence populations.

Use native Ash pagination/streaming with an explicit bounded batch size. Prefer keyset pagination over the required ordering; do not permit a fallback to `full_read`, collect a stream into a complete list, retain all pages in a cache, or open a separate transaction per page. Load only the typed values and supporting relationships required for the current page. Native queries must provide deterministic original-time/Task/placement ordering before application matching; filtering an ordered page leaves surviving observations in that order. Reduce each signal separately with lifetime/EWMA and applicable post-reinstatement accumulators carried across pages. Excluded observations consume no decay position. Page size is an application implementation parameter, not a history limit or customer setting.

| Metric or diagnostic | Bounded processing |
| --- | --- |
| Known-answer correctness and exact-question reference-match counts | Match each page against its captured effective keys, fold eligible grades or diagnostic counts, then release its values and key loads. |
| Substantive human review and reliability | Read ordered effective native outcomes in pages and fold the same eligible observations; keep automatic acceptance and neutral returns/expirations excluded. |
| Peer agreement | Read the assessed worker's answers in original order and calculate each exact peer group using the bounded methods below before folding its single eligible observation. Keep only the current outer page and current peer page, not all groups or one entire group. |
| Experience and database-expressible informational coverage | Keep native count/date/distinct aggregates; matching-dependent coverage retains compact contributing identities with the existing provenance, not answer values. |
| Combined quality, effective size and rule checks | Derive them from finished per-signal accumulators and captured configuration; fetch no historical answers. |

For exact single-choice, multiple-choice, ranking and boolean peer groups, use a two-pass majority-candidate reduction with the shared typed equality. The first bounded pass carries one complete candidate and a cancellation counter; the second counts all eligible peers matching it and verifies the configured consensus threshold. Every permitted threshold is greater than fifty percent, so any qualifying complete answer must be this majority candidate. Candidate selection alone never establishes consensus. This is the standard [Boyer–Moore majority-vote method](https://www.cs.utexas.edu/~moore/best-ideas/mjrty/index.html), avoiding an answer histogram that could grow with every distinct response. Apply the same native worker deduplication, skip/absent exclusions and exact pinned-contract filters on both passes; do not maintain an unbounded application set of seen peer identities. The resulting common reference includes all eligible workers and applies to every assessed answer under those scope settings.

For integer/decimal peers, count that same eligible distinct-peer population through native Ash queries, order by its native typed numeric value and read only the one middle value, or the two middle values for an even count, with a bounded ordered limit/offset query. Preserve decimal precision when averaging the even pair. Then scan bounded peer pages with the shared inclusive-tolerance matcher to count concentration and compare the assessed answer. Count, middle-value selection and concentration use identical eligibility within the same snapshot. Source identity may stabilize numeric query pagination among equal values; it does not change observation chronology. Do not sort the complete sample in Elixir, use a floating-point percentile approximation, or apply categorical majority cancellation to nonzero numeric tolerance.

This bounds simultaneously loaded answer populations, including a large individual peer group; it does not promise constant total process memory or constant database work. #### Scheduling and verification boundary

Use Oban with the same Repo so source facts, pending intent and durable coverage commit together. Requests arriving after scope discovery or its coverage check retain their own future execution through the enqueue contract; do not rescan indefinitely at job completion. The request transaction owns durable scheduling coverage; job completion has no separate scan/enqueue handoff.

The enqueue helper runs after the native owners, applicable settings guards and head writes, on their same Repo transaction:

1. Find and lock at most one waiting Oban row in a single query using `FOR UPDATE SKIP LOCKED`, filtering by refresh worker module, target worker identity and state in `available` or `scheduled`. There is no separate uniqueness lookup or candidate recheck.
2. If found, reuse that persisted job and hold its row lock through commit so Oban cannot claim it before the source facts/head requests become visible. Preserve its arguments and original scheduled time. Otherwise insert a new five-second job through ordinary Oban insertion with uniqueness disabled.
3. Propagate database/insertion failures so the source/request transaction rolls back. Concurrent lookups may skip a locked waiting job or see no committed row and insert duplicates; correctness does not require exactly one waiting job.

If the lookup obtains the row lock first, the job's claim and subsequent evidence capture follow the request commit. If Oban claims first, the lookup skips its locked row or excludes its executing state and inserts a future job unless another waiting job can be reused. Thus changes after capture or during completion have coverage from their own request transaction, including newly requested scopes the executing job never saw. A running, completed or retryable job alone cannot cover a new request. Ordinary Oban retries handle worker failures; a crash after publication can retry into the early no-op. Overlapping/duplicate calculations still use the existing publication guards.

For the early check, read each requested scope's current head, latest completed assessment, effective calculation settings and applicable reinstatement references in that scope's capture snapshot before its history queries, source aggregates or scoring. Preserve existing completed references/cutoffs, counters and unresolved Task discovery markers. Discovery can still make freshness pending and later request new work; an early worker no-op does not clear its flag or claim its requests are covered. For a mixture of covered and pending scopes, rebuild every enabled metric only in the pending scopes. Use the existing metadata and request-time scheduling helper, with no per-metric reuse branch, job-finish scheduling or new stored coverage state.

Keep public Oban insertion/retry APIs plus one narrow database helper for the waiting-job find-and-lock query on the current transaction connection. This infrastructure exception does not move reputation/source access out of Ash or add a shadow job resource/custom engine. Queue-row locking follows head writes and adds no later business-owner locks. Confirm claim/reuse ordering with actual independent-connection tests against the installed Oban engine. Add no advisory lock, worker coordinator, process collector or event/outbox ledger.

Settings refresh discovers affected heads in bounded batches and requests current-input calculations without holding every worker lock during the settings edit. Retain revision-specific retry identity and settings guards; do not reapply old settings or silently change frozen projects.

Benchmark the initial bounded full-rebuild scorer with coalesced worker refresh before proposing another calculation path. ## Risks / Trade-offs

- **[Majority agreement can reward conformity]** → Exclude ambiguous comparisons, require sufficient distinct peers and worker history, bound agreement below correctness, and default enforcement to reviewer information.
- **[Unreviewed returns accumulate]** → Keep total counts, worker reasons, and classification breakdown visible for reviewer investigation; do not turn frequency alone into a reliability failure or add a timed review-expiry penalty.
- **[Per-worker human-review quotas grow with workforce size]** → Omit human review from default combined quality and reuse applicable reference keys; keep actual review evidence supplementary. Future project-budget sampling provides project diagnostics without inventing individual quality or per-worker review coverage.
- **[Faulty keys or small samples misclassify workers]** → Preserve insufficient-evidence states, counts, key history, broad-failure evidence, and correction/reinstatement workflows.
- **[Workers encounter too few known-answer questions]** → Validate structurally impossible local minima, advise managers that ordinary allocation does not guarantee delivery, and expose actual evidence counts without treating missing evidence as failure.
- **[Correct answers conflict with peers]** → Use known-answer grades for designated checks and keep their peer disagreement diagnostic-only, including after key disabling.
- **[Late peer answers change earlier comparisons]** → Keep unfinished comparisons preliminary and out of scores/enforcement; evaluate only after the task reaches its target, without adding collection demand.
- **[Unequal weights overstate evidence if only raw counts are used]** → Establish EWMA from its effective sample size, validate finite/infinite capacity and show actual counts separately; do not label this a statistical-confidence guarantee.
- **[Observation-based recency can reflect old work after inactivity]** → Show original supporting dates separately from calculation cutoff; neither view certifies fresh activity, and inactivity alone does not expire a score.
- **[Lifetime/EWMA require longer captures than the former capped window]** → Reuse lightweight native queries and one shared evidence pass, measure query/transfer/scoring costs and avoid duplicate stores or speculative caches.
- **[A broader setting edit strands a frozen entry requirement]** → Validate declared history bases and attainable evidence under the same settings guard used by activation; reject incompatible edits without rewriting active rules.
- **[Source corrections race admission or recalculation]** → Mark affected calculations for refresh, prevent obsolete publication, and order completed restriction changes with issuance under database locks.
- **[Recalculation is delayed]** → Accept that an allowed worker may receive more tasks before a new restriction takes effect, or an existing restriction may last until repair/reinstatement. Keep pending updates visible and retry failed jobs; never convert that delay into a new worker pause.
- **[The first reviewer detail has no calculated metrics yet]** → Return initial-calculation-pending metadata and permitted return facts, request durable background calculation, and show completed metrics on a later read. Admission still prepares missing required inputs synchronously.
- **[An earlier denial outlives improved reputation]** → Reevaluate each new request using the latest completed inputs and retain prior outcomes only as history. Record the exact assessment references and reinstatement used for every decision.
- **[New workers cannot earn required local history]** → Permit project-local participation with insufficient evidence; use independently earned organization/global evidence for established-history entry requirements.
- **[Scoring and enforcement become a generic rules system]** → Keep a bounded configuration and application-owned algorithm; add only lifecycle-specific resources.
- **[Assignment outcomes can expose unrelated global reputation]** → Require the existing organization work relationship before any new global-dependent assignment preparation or evaluation; return an input-independent authorization denial when absent. Worker fetch establishes retained requested-work evidence under the ordinary rules, without a new consent workflow.
- **[Global scores combine incompatible local assumptions]** → Pool eligible source evidence under platform rules instead of averaging local scores; preserve source-project and pinned-question peer exclusions in every scope and keep private organization evidence inaccessible. Global history does not certify every task-specific skill.
- **[Future pay changes surprise workers]** → Keep quoted rate and bonus rules in immutable funded Finance offers; apply later changes to future work.
