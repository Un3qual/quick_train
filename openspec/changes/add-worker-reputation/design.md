## Context

See [proposal.md](proposal.md) for scope. This change owns the reputation decisions approved on 2026-10-05 and previously placed in `record-future-product-architecture`. It is an implementation proposal, not evidence that reputation has shipped. The approved compensation direction is retained below as a future Finance integration contract.

Core collection already supplies immutable TaskInputs, submitted QuestionResponses, attempt provenance, append-only ReviewDecisions, frozen Projects, and sealed exports. `QuickTrain.Tasks.Reviews.QuestionReview.initial_decisions!/2` automatically accepts answered submissions, so acceptance alone is not correctness evidence. `QuickTrain.Tasks.Access.WorkerEligibility` currently serves both allocation and existing-attempt authorization; putting reputation restrictions directly into that shared filter would revoke work already issued. `AttemptAllocation` also replays allocation request keys before selecting new work. These are concrete integration boundaries for this change.

The [worker-reputation delta](specs/worker-reputation/spec.md) defines the new behavior; [projects](specs/projects/spec.md) and [task-allocation](specs/task-allocation/spec.md) extend the implemented collection contract. This change does not depend on media execution or Finance.

The 2026-10-06 review settled known-answer evidence counts, precedence over peer disagreement, unfinished comparisons, and evidence expiration. On 2026-10-07, the user removed prior-key-knowledge handling, approved publishing assessments and automatic access decisions together, deferred customer-adjustable weights, and settled project-local admission with insufficient evidence. Global reputation and preliminary peer reporting remain in scope. A “known-answer check” means the organization's expected-answer question, not a separate kind of worker task. Its “coverage” means how many eligible known-answer questions a particular worker has actually answered; use those explicit words in API descriptions and reports.

## Goals / Non-Goals

**Goals:**

- Keep authoritative evidence in its owning domain and make assessments reproducible, scoped, and explainable.
- Implement known-answer checks and conservative peer comparison using existing immutable task identities and typed answers.
- Make project restrictions recoverable without coupling them to account bans, answer acceptance, or payment.
- Use Ash resources, actions, relationships, policies, constraints, and generators; use existing Oban infrastructure for recalculation where asynchronous work is appropriate.

**Non-Goals:**

- A second worker identity, a general rules engine, duplicated task/review event history, or a free-form score-adjustment resource.
- A canonical-answer layer or an algorithm that mistakes majority opinion for ground truth.
- Runtime Finance structures, speculative payment-provider adapters, or a generic compensation plugin interface.
- Worker-facing reputation explanations and dispute workflows; these are approved future work recorded in [future-features.md](../../future-features.md#worker-explanations-and-disputes).
- Key-exposure tracking or special scoring/key-edit restrictions for authorized staff who also perform work. Customer-adjustable organization/project weights are deferred; application developers can adjust the central weight definition.

## Decisions

### 1. Separate evidence dimensions and assessment scope

Add `QuickTrain.Reputation` for derived assessments and their evaluation workflows. Keep one global User. Project assessments are most specific; organization assessments summarize evidence within that organization; global assessments follow platform-owned rules for eligible evidence and calculation. Do not average differently configured local scores into a global score.

Expose known-answer correctness, substantive human review, peer agreement, reliability, and experience separately with sample counts and the evidence window, even when a configured calculation combines them. Use exactly three evidence states: not applicable for disabled or unselected contributors, insufficient evidence for an enabled contributor below its minimum (including zero observations), and established once its minimum is met. Counts distinguish zero observations from a small sample. Record the as-of cutoff and whether refresh is pending separately; an update does not change an established evidence state to insufficient or change access by itself. Known-answer correctness has greater influence than agreement. Strong known-answer accuracy paired with disagreement remains visible as conflicting evidence for investigation.

Attempts, submitted QuestionResponses, skips, and ReviewDecisions remain authoritative. Use effective human decisions and preserve their origin; automatic acceptances are not independent positive judgments. Skips are visible but not automatically negative. Keep contribution provenance sufficient to explain and reproduce a score without copying every source record into a parallel event store.

Alternative rejected: a single opaque reputation percentage or a global average of organization scores. Either would hide uncertainty and combine incompatible judgments.

### 2. Put known answers beside exact authored task contracts

In the current product, a batch is represented by a Project and its authored Tasks. Add keys for a Task plus its published question and exact immutable input contract; there is no need for a new Batch resource. Store typed expected answers using the existing option/input identities. An expected answer on a reusable form question alone is insufficient because correctness depends on the input revisions.

Keep distribution on ordinary task allocation for this release. Check-bearing tasks share the project's submission target and can be exhausted before later workers see them. This is best-effort evidence collection, not a guarantee that each worker sees a quiz or a configured frequency of known-answer questions. Activation must reject impossible project-local minima by comparing the required count with the number of enabled scoreable task/question keys one worker could answer, and return an advisory about shared capacity for feasible configurations. Prior organization/global evidence must be assessed under its declared scope rather than assumed absent. Show actual evaluated counts and the minimum in authorized worker assessments; skips and disabled evaluations are not tests passed or failed. Too little local evidence has the insufficient-evidence state and permits local participation rather than creating a failure-based suspension. A separately configured requirement for established organization/global evidence can still deny admission; it must be satisfiable by work outside the target project.

This deliberately avoids adding another allocator or silently increasing task demand. Guaranteed per-worker check delivery would require a separately scoped allocation design. [Qualification tests](../add-qualification-tests/proposal.md) now have an incomplete discussion skeleton and do not implicitly supply that missing guarantee.

Start with exact choice/boolean matching and configured numeric tolerance. Reuse existing answer-family validation; do not silently interpret arbitrary strings or geometry. Ranking, set/order semantics, and numeric boundary details must be listed explicitly in the supported matching contract before enabling those families. Semantic text and spatial grading remain separate future scope.

Author checks through explicit organization/project management actions. Keep key data and the check designation out of worker-facing form/task/attempt schemas and nested GraphQL traversals, including mutation results and errors. A hidden flag on a generally readable resource is not an authorization boundary. Managers/reviewers may inspect only evidence covered by their capabilities; worker-facing outputs cannot expose answer keys or peer answers.

Authorized key authors/readers may also perform work. Do not track who has seen a key, add a reveal-key workflow, exclude their answers based on key knowledge, or prohibit an otherwise authorized key edit because the actor answered that question. Keep ordinary key-authoring/correction attribution and organization authorization; the existing human-review restrictions remain unchanged. Keys and check designations stay private on worker-facing routes.

Retain evaluated key/matching-rule history. Correction or disabling records actor and reason, invalidates affected derived assessments, and reevaluates restrictions while preserving immutable submissions. Reuse the repository's deliberate action and retry conventions. Surface widespread check failures for key/instruction investigation; do not introduce automatic project pausing merely because a competitor does it.

Organization reporting was approved on 2026-10-06. Provide two bounded, scoped read views using existing evaluation evidence: a worker summary with evaluated count, correct/incorrect counts, accuracy when there is at least one evaluation, configured minimum and whether it is met; and a task/question summary with evaluated count, correct/incorrect counts and match rate so reviewers can investigate widespread failures. Both identify the applicable key/configuration provenance, evidence window and freshness; excluded evaluations do not enter their denominators. Zero evaluated answers means unavailable accuracy, and a small perfect sample can still have insufficient evidence. Use “known-answer evidence” and “question-quality reporting” rather than unexplained “coverage” or “health” labels. A low question match rate is diagnostic evidence, not proof of a bad key and not an additional automatic enforcement action. Reviewers use the already-planned correction/disabling and recalculation actions. This adds organization-side API reporting, not a frontend, extra worker interaction, separate test, or guaranteed question distribution.

Alternative rejected: overwriting a key and losing the reason for earlier scores, or using a generic form-level answer key across different tasks.

### 3. Derive agreement only from comparable distinct peers

Group by the exact task/question/pinned input contract. Exclude the assessed worker, deduplicate peers, and ignore skips and missing answers. Compare stable identities rather than randomized presentation labels. Require both enough peers and a strong enough peer consensus before a comparison contributes. Ties and split opinion are inconclusive, not errors. Numeric comparison uses a robust center such as the median with an explicit tolerance and a concentration requirement; a median alone does not prove consensus.

For a question designated as a known-answer check, use the eligible known-answer grade and exclude that question from peer-derived scoring, peer sample counts, and restrictions. This removes both contradictory penalties and double counting. Reviewers can still investigate raw key-versus-peer disagreement as a question-quality concern. Disabling a key removes its grading contribution; it does not automatically turn the same designated check into peer-scored evidence. Correcting the key repairs assessments under the same precedence rule.

Only compare completed evidence for scoring and enforcement: the task must have reached its frozen submission target, with enough distinct eligible peers and sufficient agreement. Earlier comparisons are preliminary reviewer information only. A project closed before a task reaches its target does not make that partial evidence enforceable. A current calculation may have pending comparisons; that is different from a stale calculation and does not by itself force allocation retries. This keeps a changing early majority from suspending workers and preserves the existing submission-target contract.

Measure repeated disagreement over recent comparable answers with a minimum worker sample and bounded influence weaker than correctness. A project can disable agreement scoring and enforcement for subjective questions. The normal submission target remains unchanged: a project with too few responses has no usable peer signal rather than automatically collecting additional answers.

Alternative rejected: penalizing each deviation from the current plurality or increasing collection demand to manufacture consensus. Those approaches turn sparse or subjective answers into unwarranted penalties and change the collection contract.

### 4. Freeze a small typed configuration at activation

Use direct organization defaults and draft-project overrides with one application-owned calculation. Freeze the resolved project settings under the activation transaction; later default edits affect later activations. Default editing and activation must serialize or obtain a coherent snapshot so activation cannot mix two configurations.

Keep score weights in one named application-owned definition and pass the effective weight map explicitly into the shared calculation. Do not scatter coefficients across signal handlers, admission checks, reports, or jobs. A developer should be able to change the weights and focused calculation tests in one place, without adding customer settings, database columns for each weight, a formula language, or a generic policy registry. Resolve and retain the application weights with the project's effective configuration at activation, so changing defaults in code does not silently reweight an active project. Organization/global calculations use the platform-owned weights selected for their scope and retain the actual values with calculation provenance; changing those platform weights invalidates affected assessments through the ordinary recalculation/publication path. Rebuilds use the retained effective inputs. Exact weight values and normalization for established inputs still need calibration before implementation; disabled and insufficient signals follow the availability rules below.

Disabled scoring signals are not applicable: omit their values and weights from the combined calculation. An enabled contributing signal with fewer observations than its minimum is insufficient, not zero or a reason to redistribute its weight among the remaining signals. Publish an established combined score only when every contributing enabled signal has sufficient evidence. Otherwise expose the established individual metrics/counts and an insufficient-evidence combined result with no usable number. If no signals contribute, the combined result is not applicable, not perfect. Individual signals that meet their minima can still follow their own configured actions. An admission rule requiring an established combined score follows the existing rules for insufficient local evidence and established organization/global entry requirements. Reject configuration that requires a combined score while selecting no contributing signals.

| Setting | Responsibility |
| --- | --- |
| Enabled signals | Select applicable evidence; weights come from the application-owned definition, with agreement weaker than correctness |
| Minimum worker and peer evidence | Distinguish established assessments from insufficient history |
| Agreement thresholds and numeric tolerance | Reject ambiguous comparisons and harmless numeric variation |
| Recent-history window | Allow improvement to affect assessment |
| Admission thresholds and evidence scope | Choose the qualifying assessment for new work |
| Per-signal action | Inform reviewers or suspend new project work |

Each signal is a type of evidence, such as known-answer correctness, human-review outcomes, or peer agreement. Reviewer-only signals inform an authorized person's decision; they cannot automatically restrict work. Keep them visible in reviewer metrics and, where configured, reviewer summaries, but exclude them from all automatic access decisions: individual failure rules, combined admission values and their required samples, and access-related freshness dependencies. A missing or pending reviewer-only signal cannot make otherwise sufficient admission evidence insufficient or force a retry. Known-answer failures can enforce automatic suspension after enough evidence when configured for enforcement. Disagreement defaults to reviewer information, with explicit project opt-in required for any automatic access effect.

Use the same calculation with an explicit contributing-signal set for each combined result. An admission result includes only signals enabled for automatic access decisions by the frozen project configuration; record that set so it is not confused with a reviewer summary. Apply the disabled/insufficient rules to that set. When using organization/global evidence, consume the eligible per-signal inputs rather than an opaque broader aggregate that includes a reviewer-only signal. This filters the project's access inputs without changing the independent organization/global reputation calculation or exposing private source evidence. Reject a combined-score admission requirement with no eligible contributors, and reject any gate that uses excluded contributors. No separate scoring engine or generic policy framework is needed.

Admission rules specify their evidence scope and minimum. Project-local rules allow otherwise-eligible workers to participate while local evidence is insufficient; thereafter the configured threshold applies. A project requiring established reputation from the first task must accept eligible organization/global evidence earned outside that project. If that broader history is missing, the requirement can deny admission; those workers need projects that admit newcomers. Activation rejects a project-only established-history gate that denies insufficient history, because it provides no way to earn the required local evidence. Participation with insufficient evidence never bypasses account/audience checks, another satisfied-minimum failure, or an independently configured organization/global entry requirement. This uses the existing assessment state and admission decision, not a new qualification-attempt lifecycle.

There is no customer-authored formula language, generic policy/version hierarchy, duplicate reputation-event stream, or arbitrary ReputationAdjustment resource. Retained answer-key history and calculation provenance have specific evidentiary purposes; frozen project configuration does not require a generic policy framework.

Alternative rejected: making every setting global, or exposing unrestricted customer formulas. Organizations still control applicable signals, sample minima, thresholds, windows, and actions; weights are centrally maintained until customer-specific weighting has its own scoped design.

### 5. Add a new-work gate without changing ongoing authorization

Add reputation admission to both fetch and direct assignment after ordinary account/organization/audience checks and after resolving an existing allocation retry, but before issuing new work. Preserve `WorkerEligibility`'s role in existing-attempt reads, writes, and receipts. Do not implement reputation suspension by writing an existing `ProjectWorkerAccess` block: those blocks intentionally revoke ongoing access.

Publish each project/worker assessment together with its automatic admission/restriction reasons as one derived result from the same evidence, frozen configuration, and applicable reinstatement cutoffs for access rules. Allocation uses the latest completed publication, with applicable manual reinstatement, even while replacement calculations are pending. There is no independently updated automatic-suspension record to synchronize with it. Correction, expiration, and ordinary recalculation use the same calculation/publication path. Publish conditionally and atomically so readers cannot see repaired metrics with obsolete automatic reasons or a new reason attached to an old calculation. New automatic restrictions take effect when that publication commits; they do not retroactively invalidate work issued earlier.

Calculate against one coherent, fixed evidence snapshot: retain its included source and supporting-assessment revisions, original-event evaluation cutoff, effective settings, and applicable reinstatement inputs. Order results by the captured snapshot rather than job completion time. Publish a valid snapshot that advances the last completed publication even if ordinary answers arrived or a refresh boundary passed while it ran; those changes request another calculation and leave refresh pending. Do not repeatedly discard completed work just because new observations keep arriving. A newer snapshot must not regress the published source frontier or evaluation cutoff. Corrections to evaluated keys/reviews, key disabling, changed effective settings, or reinstatement invalidate affected prepared results; reject those results and recalculate. These guards do not require an additional policy framework or copied evidence stream. Preserve as-of/pending metadata when using completed supporting assessments that already await refresh; do not relabel them as current. Allocation uses the last completed project decision while replacement work continues, without traversing supporting freshness or waiting for jobs.

Keep manual reinstatement as a separately attributable input identifying the project, worker, selected project-local automatic rule(s), actor, explanation, prior decision, and effective cutoff. For each selected rule, evaluate only evidence originally submitted after its latest reinstatement, within the existing history window and using the same minimum samples and threshold. Until those new samples are sufficient, that rule permits participation with insufficient evidence; once sufficient, it can suspend again. For answer-derived evidence use original answer submission time; other signals use their defined original source-event time. Later grading, peer completion, key correction, or rebuilding of an earlier answer cannot count as new post-reinstatement performance. Repeating the same reinstatement request must retain its original cutoff rather than continually restarting the period.

The cutoff changes the selected rule's enforcement evidence, not the worker's historical reputation, reviewer metrics, or source answers. Other automatic reasons, explicit account/audience blocks, and independently configured organization/global entry requirements still apply. For a selected combined local rule, each eligible contributing signal must meet its existing minimum from post-reinstatement evidence. Use the shared history-selection/calculation boundary for this restriction on evidence; do not add a recovery score, separate recovery thresholds, or a timed blanket exemption. Include the applicable reinstatement input in conditional assessment/access publication and serialize it with admission so old calculations cannot restore an obsolete reason. A deliberate later reinstatement can begin another period. No platform-wide account ban follows automatically.

Preserve the issuance boundary under races. Allocation currently locks the Project, then the worker User, then task capacity. Choose a compatible ordering for restriction changes and assessment publication, with post-lock checks and stable ordering for multi-worker recalculation. Do not introduce a lock inversion through review/submission callbacks, which hold their existing outcome/task locks. Background publication must advance the completed snapshot and honor correction/settings/reinstatement guards; ordinary new answers alone do not prevent publication.

Pending recalculation never creates a new restriction, a temporary reputation-updating response, or a grace-period timeout that later pauses work. An allowed worker continues receiving otherwise available work under the last completed decision while a refresh is pending or delayed. An already restricted worker remains restricted until a replacement decision or applicable manual reinstatement removes the reason; delay alone does not clear it. Account, organization, audience, explicit-block, lease and capacity checks still run normally. After allocation lock waits, read the latest completed decision and applicable reinstatement so a newly published restriction cannot be missed. Submission and review retain their current acceptance semantics.

For first-time access, perform scoped authorization checks and detect committed allocation retries before expensive preparation. If no project decision exists, use the shared calculation to prepare it and any missing initial supporting assessments before entering the allocation transaction or taking Project/User/task allocation locks. Read a coherent evidence snapshot without holding those allocation locks. Reuse completed supporting assessments, retaining any pending/as-of metadata, rather than waiting for their queued refresh. Unprocessed history is not absent history. Insufficient local evidence permits participation; genuinely insufficient required organization/global evidence can deny entry.

After acquiring allocation locks, recheck account/audience/management authority, project state/configuration, the allocation request key, the latest completed decision, and applicable reinstatement. If a concurrent publication or committed allocation already supplies the result, use it instead of the prepared candidate. Otherwise validate the candidate's correction/settings/reinstatement guards and publish it under the snapshot-order rule before deciding issuance. If a guard changed and there is no usable completed decision, release the allocation locks before preparing again in the same request. Do not perform evidence scans or scoring while holding those locks, introduce a queued warm-up lifecycle, or return a reputation-updating pause.

Time itself can make a calculation stale. For a time window of duration W at server cutoff T, include evidence whose original event time is in (T-W, T]. Answer-derived evidence uses the original submission time; later key/review correction or completion of a peer set does not reset that age. Other time-windowed evidence uses the original event time specified for its signal, not the recalculation/job time. Retain the evaluation cutoff and next time-dependent invalidation, no later than the earliest included observation's expiry. Schedule recalculation for that boundary; reads can detect a missed boundary and request repair without pausing allocation. These deadlines describe calculation freshness, not an access lease. Publication follows the fixed-snapshot ordering above: an older snapshot cannot overwrite a newer publication, while time passing merely marks a completed snapshot for further refresh. A count-only window has no clock-driven expiration, but must still use a deterministic original-event order.

Keep history selection behind one small function that takes the window description and evaluation cutoff, and returns the selected observations plus any next time-dependent invalidation. The shared scorer receives those observations explicitly rather than querying time or applying its own window filter. Recalculation and publication consume the returned freshness facts together with supporting-assessment provenance; admission uses the completed result without branching on window type or waiting for refresh. Use ordinary functions and explicit data rather than a plugin/strategy framework. Both time-based and count-only windows remain in scope; this boundary supports either type without spreading its rules through scoring, reporting, or access decisions.

On expiration, schedule recomputation and publish the score, sample minimum, and every affected automatic reason together, retaining the applicable reinstatement cutoffs. That completed publication removes a failure-based reason that no longer meets its threshold or minimum; other active reasons and explicit blocks remain. Until then, the previous decision stays effective. If the replacement has insufficient project-local evidence, the affected local rule permits participation; a separate organization/global established-evidence requirement may still deny entry. The same original observations cannot regain recency merely through correction or repeated recalculation.

Use independent database connections and deliberate barriers to verify suspension versus issuance, stale versus corrected publication, key/default edits versus activation, and retry recovery. Replaying an already committed allocation after a reputation-only suspension must return its currently authorized result, not attempt new issuance or extend the lease.

Alternative rejected: pausing work until scoring jobs finish, using a grace-period expiry to introduce that pause later, cancelling in-flight work, or reusing the revoking audience block for reputation. Refresh delays remain visible to reviewers while completed decisions continue to govern access.

### 6. Keep compensation commitments in Finance

Optional reputation-based pay bands and quality bonuses are approved. Organizations provide defaults and projects may override them; the future Finance activation contract resolves and freezes rate rules. A project can offer a standard rate and higher rates for sufficiently established project- or organization-scoped quality. Initial upgrades use known-answer correctness and substantive human review with minimum evidence. Peer agreement remains a monitoring and eligibility signal until its suitability for compensation has been established for that project. Competitor rates and thresholds are not QuickTrain defaults.

Historical reputation selects the rate for a future offer. A quality bonus evaluates performance on the offered work using criteria disclosed with that offer. Eligibility for better-paid projects is another use of reputation and does not imply a different price for identical work. Admission, answer acceptance, and monetary settlement are separate decisions.

Finance must show and freeze the quoted rate and bonus criteria when work is offered/fetched, with enough evidence to explain the selected band. It must reserve the maximum organization charge, including any promised conditional bonus, atomically with issuance. Later score/configuration changes affect future offers and cannot alter an issued offer's quoted rate or bonus rules. Skips, rejections, and partial answers remain task facts; the pinned rate terms determine payment treatment.

Reputation supplies scoped evidence and calculation provenance. Finance owns WorkOffers, funding reservations, settlement, ledger accounting, and payouts. This change adds no paid-offer or bonus tables and does not require a Finance implementation to complete. The future Finance change must restate these terms as behavioral specs and test rate changes, conditional bonus settlement, reservation failure, and offer/reputation races against the implemented reputation API.

Alternative rejected: retroactive rate reductions or adding a payment subsystem to make reputation useful. Frozen offers keep commitments predictable and let reputation ship independently.

### 7. Use scoped Ash operations and additive storage

Generate the Reputation domain/resources and migrations with the installed Ash tooling, then tailor them to the approved scope. Keep settings, keys/history, assessments containing automatic access reasons, and manual reinstatement records distinct only where their lifecycles or authorization require it; do not create an additional automatic-suspension projection or generic policy-resource family. Use Ash UUID identities, explicit organization/project references, database constraints, and native actions/domain interfaces. No direct-Ecto exception is proposed.

Reuse the organization-capability path for management and review operations with explicit grants and fail-closed scope. Preserve external worker access through existing audience/attempt authority. Expose deliberate bounded GraphQL reads and mutations; authoring authority does not imply general read access. Do not expose global raw evidence or let a local setting change platform-owned calculations. Exact capability names and global-summary disclosure must be fixed in the implementation contract.

The explanations delivered by this change are for authorized organization reviewers. Detailed worker-facing reputation explanations and worker-initiated disputes are deferred. Workers still receive ordinary work-access outcomes; this does not add a personal evidence breakdown or an appeal action. Organization reviewers retain evidence inspection, key correction, and reinstatement without depending on a future dispute workflow.

Use responsibility-specific Oban jobs for affected-scope recalculation and repair. Keep small source changes transactional with their invalidation/scheduling facts; repeated delivery must converge. Prefer rebuilding from source facts over incremental counters that cannot be reconciled.

### Future question capabilities

[Multiple acceptable known answers and question-level scoring controls](../../future-features.md) are recorded outside this change. Acceptable-answer sets belong to question/key authoring and grading; reputation will consume their grading outcome when implemented.

Question-level controls are approved future work requiring a published-question contract change. That work must also modify reputation's question selection, denominators and minimum-evidence counts, scoring and enforcement eligibility, explanations, and rebuild behavior. Resolve the controls through the pinned question version and effective project configuration, preserving already-active contracts. This release retains project-level settings; for a form mixing factual and subjective questions, disable agreement scoring/enforcement for the whole project until selective controls exist rather than treating every question as objective. No question schema or extra override hierarchy is introduced here.

## Research Rationale

These first-party sources were reviewed during the approved discussion on 2026-10-05. This change relocates that research; competitor numerical thresholds, permanent exclusions, and commercial terms are not QuickTrain requirements.

- [Appen Quality Flow](https://success.appen.com/appen-success-center/settings/guide-to-test-questions-in-quality-flow) links known-answer accuracy with job access and repairs scores/access after faulty-key corrections. Its [test-question guidance](https://success.appen.com/appen-success-center/settings/guide-to-test-questions-in-quality-flow/test-question-best-practices) also describes job pausing for widespread misses/contests. This supports recoverable enforcement and key-quality inspection; automatic project pausing is not adopted here.
- [Toloka Quorum](https://platform.toloka.ai/docs/reference/nodes/quorum/) demonstrates exclusion from future work for repeated disagreement separately from grading existing answers. [MTurk eligibility](https://docs.aws.amazon.com/AWSMechTurk/latest/AWSMechanicalTurkRequester/SelectingEligibleWorkers.html) and [consensus policies](https://docs.aws.amazon.com/AWSMechTurk/latest/AWSMturkAPI/ApiReference_HITReviewPolicies.html) separate access requirements from optional scoring actions and exclude inconclusive questions from agreement scores.
- [Labelbox's quality strategy](https://labelbox.com/guides/how-to-create-a-quality-strategy-for-your-data-labeling-project/) emphasizes investigation, feedback, and retraining and distinguishes subjective agreement from accuracy. [Prolific's quality controls](https://researcher-help.prolific.com/en/articles/445223-bulk-rejecting-exceptionally-fast-submissions) illustrate reviewer information with optional automation. These support conservative disagreement defaults.
- [Toloka's marketplace pricing documentation](https://github.com/Toloka/docs/blob/main/en/guide/concepts/dynamic-pricing.md) describes skill-dependent bands fixed at assignment. This is an older marketplace precedent; availability in its newer node platform was not confirmed. [MTurk bonuses](https://docs.aws.amazon.com/AWSMechTurk/latest/AWSMechanicalTurkRequester/IntroCoreConcepts.html) and [Prolific performance payments](https://researcher-help.prolific.com/en/articles/445234-can-i-make-partial-payments-to-participants) support base pay plus performance bonuses. [Remotasks](https://www.remotasks.com/en/projects/90551) describes quality unlocking better-paid tasks. [Outlier](https://outlier.ai/) advertises quality-based rewards without a precise public historical-score-to-rate formula in the reviewed pages. These are different mechanisms, not one universal reputation multiplier.

## Risks / Trade-offs

- **[Majority agreement can reward conformity]** → Exclude ambiguous comparisons, require sufficient distinct peers and worker history, bound agreement below correctness, and default enforcement to reviewer information.
- **[Faulty keys or small samples misclassify workers]** → Preserve insufficient-evidence states, counts, key history, broad-failure evidence, and correction/reinstatement workflows.
- **[Workers encounter too few known-answer questions]** → Validate structurally impossible local minima, advise managers that ordinary allocation does not guarantee delivery, and expose actual evidence counts without treating missing evidence as failure.
- **[Correct answers conflict with peers]** → Use known-answer grades for designated checks and keep their peer disagreement diagnostic-only, including after key disabling.
- **[Late peer answers change earlier comparisons]** → Keep unfinished comparisons preliminary and out of scores/enforcement; evaluate only after the task reaches its target, without adding collection demand.
- **[A window expires while a worker is inactive]** → Track the next invalidation, schedule repair, and let reads detect missed refreshes without pausing access or waiting for a new submission.
- **[Source corrections race admission or recalculation]** → Mark affected calculations for refresh, prevent obsolete publication, and order completed restriction changes with issuance under database locks.
- **[Recalculation is delayed]** → Accept that an allowed worker may receive more tasks before a new restriction takes effect, or an existing restriction may last until repair/reinstatement. Keep pending updates visible and retry failed jobs; never convert that delay into a new worker pause.
- **[Scores and access reasons drift apart]** → Publish them as one derived project/worker result and retain manual recovery as an attributable input.
- **[New workers cannot earn required local history]** → Permit project-local participation with insufficient evidence; use independently earned organization/global evidence for established-history entry requirements.
- **[Scoring and enforcement become a generic rules system]** → Keep a bounded configuration and application-owned algorithm; add only lifecycle-specific resources.
- **[Global scores combine incompatible local assumptions]** → Evaluate eligible evidence under platform rules instead of averaging local scores; keep private organization evidence inaccessible.
- **[Future pay changes surprise workers]** → Keep quoted rate and bonus rules in immutable funded Finance offers; apply later changes to future work.

## Migration Plan

This request creates planning artifacts only. Runtime implementation will add resources and explicit capability grants without modifying existing global users, form/question identities, task inputs, submitted answers, review chains, or sealed export bytes.

Existing active projects retain their pre-reputation admission behavior. New draft configuration resolves on activation; adding defaults must not silently opt active projects into enforcement. Historical evidence can be assessed only under the explicitly chosen scope/window/provenance rules, never by inventing historical known-answer keys. Global eligibility and disclosure must be settled before enabling global admission.

Test migration up/down/reapply in a disposable database containing existing collection evidence. Deployment rollback must preserve newly created keys, correction histories, and reinstatement records rather than dropping authoritative evidence. Keep additive tables and disable use through a controlled deployment rollback; reconcile pending jobs before resuming enforcement. No production cleanup/destructive downgrade is authorized by this plan.

## Decisions to Finalize Before Implementation

The discussion approved the behavior and boundaries above, not a calibrated formula. The first task must record these choices and reconcile the affected scenarios before runtime work begins:

- Exact score normalization/combination for established inputs, reliability semantics and original-event timestamps, application-owned weight values and validation, minimum sample defaults, window duration/count defaults, and score-threshold inclusivity. Central weights, the three evidence states, separate pending-refresh metadata, combined-score availability, time-window boundaries, and expiration behavior are settled above.
- Supported choice cardinality/order matching, numeric tolerance boundaries and consensus concentration, and which effective peer answers qualify. Free-text/spatial semantic grading remains out of scope.
- Organization aggregation and global eligible-evidence/disclosure rules; avoid aggregating differently configured local scores. Preserve project-local participation with insufficient evidence and independent organization/global entry evidence as specified above.
