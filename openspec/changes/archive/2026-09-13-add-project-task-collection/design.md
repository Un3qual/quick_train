## Context

See `proposal.md` for motivation and scope. The source is `../record-future-product-architecture/design.md`, especially A and C–J, M–O. Authentication, normalized datasets/assets, and versioned forms were implemented before this change. This implementation adds Projects and Tasks to the explicit GraphQL schema.

Existing Forms exposes stable FormVersion, InputSlotDefinition, InputFieldRequirement, PresentationElement, QuestionDefinition, QuestionOption, and Label identities. Its typed constraints already define Unicode code-point spans and normalized spatial coordinates. Datasets provide single-valued flat records and immutable revisions. Assets currently certify only immutable bytes, not image dimensions or rendering safety. Existing resource policies and the shared OrganizationCapability check require organization membership for management. The external-worker route specified here is an explicit product relationship, never a relaxation of that shared check.

The user revised the release order: this change must be implementable and complete before detailed media support. Image presentation, image choice, spatial responses, and mask uploads are tracked in [add-project-task-media](../../add-project-task-media/proposal.md). Only that follow-up depends on the separately scoped verified-media/storage foundation.

## Goals / Non-Goals

**Goals:** Keep canonical evidence relational and immutable, keep projections rebuildable, use existing Ash lifecycle patterns, and make concurrent allocation, submission, and review unsurprising. Each implementation phase is independently testable while the complete collection scope remains tracked here.

**Non-Goals:** A generic workflow engine, plugin registry, scheduling framework, event-sourcing layer, mutable project-version graph, or alternate identity/authorization system. No JSONB product content; Oban's own transport arguments remain ordinary framework infrastructure.

## Decisions

### 1. Two domains with named boundaries

`QuickTrain.Projects` owns project configuration and worker admission. `QuickTrain.Tasks` owns issued work, evidence, review, projections, and exports. Tasks depends on Projects, Forms, Datasets, and Assets. Projects depends on immutable Forms/Datasets definitions, not on task resource ownership. Project completion can invoke a narrow Tasks cancellation workflow in the same database transaction. Finance/Reputation get no placeholders or callbacks in this release.

Use generated Ash domains/resources, code interfaces, policy checks, transactional actions/changes, AshPostgres relationships and checks, and explicit AshGraphql allowlists. Keep named workflows near their owner: `Projects.ProjectActivation`, `Tasks.TaskSelection`, `Tasks.AttemptAllocation`, `Tasks.ResponseSubmission`, `Tasks.QuestionReview`, and `Tasks.ResultExporting`. Use ordinary functions for shared type checks rather than a generic service layer.

Alternative: one large product domain would obscure ownership; more orchestration domains would add indirection without independent state. Two domains preserve the recorded dependency direction.

### 2. PostgreSQL owns UUID generation

Apply the `database-identities` contract to persisted resources in existing Accounts, Organizations, Authorization, EnterpriseIdentity, Forms, Datasets, and Assets, and to every new Projects/Tasks resource. Use native PostgreSQL `uuid` columns with `gen_random_uuid()` defaults. Configure Ash UUID attributes as `generated? true` without an Elixir default, retaining primary-key/non-null semantics and public ID reads. Remove client-writable IDs from creation inputs except private paths carrying a value already generated by PostgreSQL. The current `uuid_primary_key` shorthand supplies an `Ash.UUID.generate/0` default, so existing migration defaults alone do not move generation into PostgreSQL. Keep the database default explicit in AshPostgres migration metadata so code generation preserves it. Use ordinary Ash creates with returned records, requesting returned bulk records or fetching after creation where needed; do not generate fallback IDs in Elixir.

Create parent rows first and build dependent references from their returned IDs in the same transaction. For `Forms.Graph.copy!`, replace the precomputed Elixir UUID map with creation in the existing resource dependency order and an old-to-returned-ID mapping. Match returned records to source rows explicitly; do not assume an unordered bulk return preserves input order. Keep the current graph-copy transaction, validation, and immutable source identities. Embedded projections such as AssetSummary carry existing IDs and need no generator.

Assets currently needs an ID before inserting its non-null staging destination. For ordinary Assets registration, obtain that UUID in a short PostgreSQL call, finish the database call, then derive the staging path and obtain/validate upload access before inserting the pending Asset with that exact obtained UUID as its ID. This private create supplies the database-issued ID explicitly, so the staging destination and stored Asset identity use the same UUID. This preserves the existing no-row failure for malformed or insecure descriptors. The unused UUID needs no reservation record or cleanup. Task-owned creation uses its existing workflow transaction to persist the Asset, staging identity, and ownership before storage I/O; later access failures return no descriptor and preserve that committed record for the same workflow's retry path. All descriptor validation and storage I/O stay outside database transactions. These paths require no nullable staging state or new reservation resource. Likewise, generate the internal finalizer claim UUID in PostgreSQL while holding the existing asset lock and use the returned claim for fencing. Prefer supported AshPostgres database expressions; use a narrow database call only where the existing action cannot express generation. Preserve locking, expiry, deduplication, and retry behavior. No public UUID issuance endpoint or generic UUID service is needed.

Caller-supplied retry UUIDs remain request inputs available before the first side-effectful call. They are stored under existing scoped uniqueness rules and never replace database-generated record IDs. Elixir validates them but does not create them. Changing generation does not rewrite existing IDs, published references, or sealed exports; framework internals and non-UUID authentication secrets are outside this identity policy.

### 3. One frozen project is one collection run

| Owner | Persisted concept and essential fields |
| --- | --- |
| Project | UUID ID, organization, title, dataset, published schema version, published form version, state, audience, external-access mode, selection/review modes, coverage target, lease duration, timestamps |
| ProjectItem | project, stable dataset item, exact revision; unique project/item |
| ProjectInputBinding | project, requirement, field definition; unique project/requirement |
| ProjectSlotPolicy | project, input slot, exact item count, shuffle flag |
| ProjectQuestionPolicy | project, question, accepted-answer target, skip allowed, reason required, failure threshold |
| ProjectWorkerAccess | project/user, disposition `allow` or `block`; absence is neither; unique project/user |
| ExplicitGroup / ExplicitGroupInput | authored group position and exact cohort-item/slot membership; never a pre-created Task |

A project pins exactly one published dataset schema version. Every cohort revision uses that version, so one binding per requirement is sufficient. Each item occurs once in the cohort, and a group uses distinct items across all slots. One fixed count per slot lies within the form's minimum/maximum; no runtime variable group sizes or slot-specific query language. Bind every requirement to an exact root field of the same family/cardinality. A required requirement needs a required field; optional requirements can bind required or optional fields. Every cohort item must satisfy each slot's bindings because the initial selector can place any cohort item in any slot.

Draft enrollment/removal uses explicit revision IDs in batches; it never interprets "latest" after activation. Activation locks Project, reloads all configuration/cohort pages, validates relationships, field readiness, complete policies, group feasibility, and published constraints, and freezes everything except title, lifecycle, and worker-access overrides. Every child edit takes that same lock and rechecks current `projects.manage` authority; edits to frozen configuration children also require draft state. ProjectWorkerAccess is exempt from that draft-state guard and remains mutable after activation so an allowlist can admit or revoke users; blocks always win. Audience and external-access mode themselves remain frozen.

Later enrollment or changed bindings/targets uses a new draft project with a new identity. No configuration versions, enrollment snapshots, or implicit carryover of task progress. A convenience clone operation is outside scope.

Lifecycle: `draft -> active`, `active <-> paused`, `active|paused -> completed`, `completed -> archived`. After current management authorization and under the Project lock, each lifecycle action returns the unchanged project if its target state is already current, without repeating freezing, expiry/cancellation, or timestamp changes. Other transitions remain invalid. This provides retries in the current target state without a request ledger or replay across intervening transitions. Pause prevents new allocations but permits live leases to finish. Completion deliberately closes remaining demand, atomically expires overdue live rows before cancelling unexpired live attempts and unsatisfied tasks, and keeps submitted responses reviewable. Completion itself preserves satisfied tasks; later review corrections recompute their state using the precedence below. Archive is a retention state, not deletion; managers can still inspect/export/review submitted evidence. Completion does not require coverage satisfaction or an unnecessary pause, and no automatic completion is inferred from a temporarily empty fetch.

Alternative: mutable configuration snapshots support continuous enrollment but introduce identity/version/transition machinery; new projects make the frozen contract explicit with existing lifecycle concepts.

### 4. Management and worker access are separate

Management capabilities are `projects.read`, `projects.manage`, `tasks.assign`, `tasks.review`, and `tasks.results.read`. All require the active account, owning organization, membership, and exact capability through the existing check. Each mutation authorizes its own returned result; manage/assign/review does not silently grant unrelated browse access. Selecting dataset and form resources during draft authoring also requires their existing read capabilities. Provision catalog entries and explicit role grants using existing operator primitives; do not auto-grant roles or depend on the separate operator-bootstrap change.

Worker eligibility is evaluated with explicit organization/project and the authenticated User, never a supplied worker ID for self-service actions. `organization_members` accepts active members; `external_users` accepts any active user through open access or that user's allow entry, even if the user is also a member; `both` is the union. A block overrides all routes. No geography, qualification, or reputation rules are introduced. Direct assignment requires `tasks.assign` for the caller and applies exactly the same eligibility/capacity checks to the target worker. Linked follow-ups additionally require `tasks.results.read` so the manager can discover a terminal predecessor through existing audit task/attempt connections; assignment permission alone still grants no browsing.

Every allocation rechecks current eligibility and an active project. Existing live attempts permit reads/writes while the project is active or paused, but still recheck account, organization, current audience route, block status, ownership, and lease. Membership removal only disqualifies a worker if no external route remains. Revocation rejects new work access without erasing evidence. Already-issued storage descriptors can remain usable until expiry; cap them at the earlier of five minutes and the lease deadline and never describe revocation as retroactively revoking signed URLs.

Tasks exposes a typed attempt work bundle with only pinned published form definitions, offered question IDs with their frozen `skip_allowed` and `reason_required` booleans, actual input order, and bound values. Resolve those two values through each offered question and its frozen project policy; no copied policy snapshot or general project/policy traversal is needed. Workers can determine skip/reason rules before attempting a save or submission. It must not return generally browsable Form/Dataset/Asset resources with their authoring/reverse relationships. Use narrowly scoped Ash read actions and typed nonpersistent result resources where projections are needed. Any internal authorization bypass follows one explicit attempt-ownership check and selects by attempt/task/project IDs, not arbitrary user-provided resource IDs. No worker-provided context flag grants authority.

After a terminal attempt, workers can read a receipt containing their own attempt ID, state, timestamps, and review statuses, but cannot renew source access or change/read draft content through the work bundle. Receipt reads still require an active account/organization, ownership, and a current unblocked audience route; they do not require a live lease or an active project. Organization result readers retain evidence access. Omitted/foreign IDs fail with the same sanitized not-found/forbidden shape.

### 5. Issued groups, question capacity, and coverage

Task owns immutable TaskInputs (cohort revision and slot), TaskQuestionProgress, and Attempts. Tasks also owns one TaskItemCoverage projection per ProjectItem. Each Attempt owns immutable AttemptQuestions (the question set offered at allocation), AttemptInputPresentations (TaskInput, displayed position within slot), and one Response. AttemptQuestions is the small relational record needed to explain why an attempt answered only some form questions; it is not a question copy.

For each question, available capacity is `target - accepted - pending - live reservations`, floored at zero. Before deciding capacity or attention for an existing candidate Task, allocation expires every overdue physical live attempt on that Task across all workers and updates the offered questions' failure counts, reservations, and derived attention under the same Task/progress locks. Allocate an attempt only when at least one question has capacity and freeze exactly those question IDs. Each live AttemptQuestion reserves one unit; submitted answered outcomes become pending or accepted, while skips/expiry/release/cancellation release the reservation. Pending manual reviews therefore prevent over-issuing work. All offered questions, and only those, need explicit outcomes at submission. A later rejection opens capacity again. No cap truncates accepted evidence: a correction can cause accepted counts to exceed the target and every accepted answer stays visible.

Per-item coverage counts appearances in distinct issued TaskInputs, including issued tasks later cancelled, and is independent of answer replication. Retrying an existing task or creating follow-up attempts does not increment coverage. A balanced project's positive coverage target is a lower goal, not a hard upper bound: filling a group around an under-covered item can expose other items above target. Explicit selection requires its complete authored groups to cover every cohort item at least that many times before activation.

Task grouping identity uses slot IDs and sorted cohort-item IDs within each slot, separate from randomized presentation. Use a versioned length-delimited encoding and hash plus equality verification; enforce unique project/group identity. The same exact group is one Task with multiple attempts, not duplicate task rows. Reject duplicate explicit groups at draft authoring/activation. Never create unused random groups or deterministic generation schedules.

`TaskSelection` has a small internal strategy contract: given frozen project configuration, eligible candidate items/groups, and coverage, return a canonical group or a typed no-work reason. Dispatch only `balanced` and `explicit`; reject unknown modes. No persisted plugin registry or future algorithms.

Fetch and direct assignment first reuse open non-escalated tasks with question capacity that this worker has never attempted. Otherwise balanced selection anchors on an under-covered cohort item, fills each slot from least-exposed distinct candidates, samples ties afresh per fetch, and creates only the group issued. If a preferred group already exists, search alternative companions and exposure tiers within the existing operation timeout instead of repeatedly selecting that same group. Tie sampling must not create a stored random schedule. Once every item meets its coverage goal, balanced selection creates no more groups. Targets belong to exact task/question identities, so different groups cannot repair unmet targets on existing tasks; use other eligible workers or the existing deliberate follow-up path. Explicit selection consumes the next unissued authored group by position. Issuance and consumption commit together. Workers ordinarily never receive the same task twice, including after a skip, release, or expiry; deliberate follow-up is the sole exception.

Use the existing operation timeout for selection; if interruption or contention prevents deciding, return `retry_later` without claiming exhaustion. Do not introduce a fixed candidate-count ceiling. A complete scan finding no worker-specific work returns `no_work_for_worker`; all current demand being reserved/pending returns `waiting_for_answers`; proved coverage/group exhaustion with unmet demand returns `needs_attention`. Do not mark globally impossible work because one worker has exhausted eligible tasks. Selection tests assert these invariants, not a random sequence.

Alternative: pre-materialized pairs consume space proportional to combinations and invent evidence for work never offered. Fetch-time grouping stores only actual work.

### 6. Transaction order, leases, and retry identity

Use Ash transactions and locked scoped reads. Related-data checks happen after locks. Ordinary mutation paths hold a shared Project row lock; draft edits, admission overrides, activation, and lifecycle transitions take an exclusive Project lock. This lets lifecycle/admission changes serialize with worker commits without serializing all ordinary answers on the Project row. Lock order is Project, worker User (for allocations), existing Task/progress in stable IDs or new-group cohort coverage in stable IDs, Attempt, Response, QuestionResponse. A path selecting a new group does not return to existing-task selection while retaining coverage locks; retry from the start instead. Review and submission take Task before Response. Source FormVersion/revisions are immutable and need no write locks.

Use task/coverage `FOR UPDATE SKIP LOCKED` for competing selectors through the data layer's supported locking facility. Revalidate capacity and canonical-group uniqueness under those locks. When a supported Ash API cannot express the required locking or export snapshot isolation, a small parameterized query/transaction helper through the existing Repo is a justified boundary exception; business rules, resources, and writes still belong to Ash. No handwritten Ecto replacement, triggers, or stored business functions.

One live attempt per project/worker is enforced by locking the worker during allocation and a partial unique index on live states. Before inserting, transition any past-deadline live row for that worker to expired under its Task/Attempt locks so stale physical state cannot violate the index. In addition, after locking a candidate Task/progress and before capacity or attention checks, take a database wall-clock cutoff and expire all of that Task's physical live attempts whose deadlines are at or before it, regardless of worker. Update affected offered-question reservations, expiry failures, attention, and Task state exactly once using the existing expiry transition and stable lock order. Use indexed updates scoped to this Task and the existing finite operation timeout; no project-wide scan or locks on other worker Users are needed. A no-work result can commit these expiry updates without issuing an attempt, and later cleanup jobs are no-ops for already-terminal rows. Concurrent projects may briefly contend on that user's row, an acceptable first-release trade-off. Admission changes lock Project exclusively; account/organization/membership state is reread for each request. Authorization is evaluated at the transaction's authorization point; existing foundation status changes need not gain a new global lock protocol. Subsequent requests must see revocation.

Attempts start `claimed` (pool) or `assigned` (manager); start/first save makes them `in_progress`. Live states transition to `submitted`, `expired`, `released`, or `cancelled`; terminal states never revive. Lease duration defaults to 30 minutes, frozen on Project within 1–120 minutes; no heartbeat/renewal protocol. Enforce the deadline using database wall-clock time after acquiring locks, including a request that waited across expiry. A unique Oban expiration job is cleanup only; actions deny overdue leases, and allocation synchronizes their expiry evidence before evaluating both capacity and attention even when the job has not run. Release, expiry, and cancellation retain stored draft rows but never expose their payloads as submitted or public audit evidence; audit access covers the terminal attempt, offered questions, and presentation. Completion holds the exclusive Project lock and takes one database wall-clock cutoff. In the project transition transaction, first expire physically live rows whose deadlines are at or before that cutoff, preserving their failure contribution; then cancel the remaining unexpired attempts and unsatisfied tasks and update reservations/progress. A lease crossing its deadline later during that transaction is classified at this same cutoff. No terminalization state is deferred to cleanup; failure rolls back the entire completion. The project lock prevents concurrent submit from committing after completion.

Use indexed set-based updates limited to affected attempt states, their offered-question reservations, and unsatisfied task/progress rows. Do not rescan submitted answers/review history, load the full project graph, or rebuild all projections during completion. Work grows with the affected live/overdue attempts and unsatisfied tasks; the exclusive lock can block project writes until commit. Retain finite database/operation timeouts and rollback on timeout. Operators may use the existing pause action and let leases finish/expire before retrying completion to reduce live work, but pause is not required. A new drain state, background cancellation workflow, or partial canonical completion is outside scope; measure this deliberate bulk operation before adding that machinery.

Allocation, review, and export accept required caller-supplied UUID request keys, distinct from database-generated record IDs, through Ash `:uuid` arguments and native PostgreSQL UUID columns. These typed identities replace arbitrary text keys and their length rules; use the existing scoped identities without a hash column or generic retry ledger. Invalid UUID inputs fail ordinary argument validation before mutation. Store the allocation key and normalized request identity on Attempt, unique per project/requesting actor/key; operation, target worker, and explicit follow-up target participate in the identity. A retry returns the same attempt's current receipt/bundle after current authorization and never renews it. Reusing a key for different arguments returns `idempotency_conflict`. A no-allocation result need not consume a key. Submit uses the Response identity: retry returns its existing immutable result. Draft saves take the shared Project lock followed by Task, Attempt, and Response locks, hold them through commit, and recheck project state, current eligibility/ownership, live attempt state, database wall-clock deadline, and draft state after locking. They replace one whole question outcome and require `expected_revision`; increment the response revision atomically and reject stale writes. Review uses its own decision identity below. No generic idempotency ledger is needed.

### 7. Typed drafts, skips, and text spans

One Response per Attempt transitions `draft -> submitted`. QuestionResponse is unique per response/question and stores `answered` or `skipped`, the family, and exactly the matching scalar columns or child relation. Text, integer, decimal, and boolean use nullable typed columns with local exclusivity checks; multi-valued answers use StaticOptionAnswer, TaskInputAnswer (ranking adds position), and TextSpan. Avoid four scalar wrapper tables with no independent identity. Foreign keys carry response/task/form-version scope where needed so a valid foreign UUID cannot bind a different graph. Dataset values and response values remain separate resources.

Submission takes a shared Project lock, then locks Task, Attempt, and Response, rereads current lease/access and the complete offered question set, and validates every answer against the pinned published constraints. Reject missing outcomes, extra questions, incompatible typed children, duplicate choices/ranks, labels/options from another question/version, and TaskInputs outside the referenced slot. Ranking is a complete unique permutation of that slot's inputs. Preserve decimal precision, signed 32-bit integers, exact text and whitespace; reject NUL/non-finite numerics. Text constraints and spans count Unicode code points, not bytes or graphemes. Save may retain an incomplete answer, but must enforce local types, ownership, applicable published constraints, and no malformed children; submit enforces completeness/count bounds. Every child edit and delete uses the same Project/Task/Attempt/Response lock order and post-lock checks as draft replacement; no stale record can bypass terminal attempt or submitted response state.

Skipping is explicit and contains no answer children. If allowed by the frozen question policy, accept optional nonblank reason text (required when configured), optional explanation, and a server timestamp. Replacing an answer with a skip removes its draft children atomically; submitted skips never disappear. All-skipped submissions are valid where every offered policy allows them, satisfy zero answer targets, and contribute to escalation. Optional absent dataset values are represented as absent; required annotation/question source requirements are never silently synthesized.

Text spans reference TaskInput, its exact bound DatasetValue, and a label from the question's label set. They satisfy `0 <= start < end <= source code-point length`; overlaps are allowed, exact duplicate input/value/label/range tuples are rejected. Zero spans is a valid answered outcome only when the form minimum is zero. Text-span execution uses immutable text and has no image-format dependency.

Activation uses a closed supported-contract check over the entire published form. Reject any `image` input requirement (including one displayed through a `bound_value` element), `image_choice` renderer, or bounding-box/polygon/raster-mask family with `unsupported_task_contract`. Do not silently omit unsupported questions, call a media service, or enable them merely because a provider is installed. Their published Forms definitions remain valid; the later task-media change extends execution deliberately.

Do not generate spatial tables, mask-attachment resources, worker mask-upload actions, or media callbacks in this change. The follow-up owns their normalized geometry/provenance and verified-source integration. This keeps the first implementation complete with no permanently unchecked media tasks or speculative resource scaffolding.

### 8. Review and escalation preserve evidence

QuestionResponse has append-only ReviewDecisions containing accept/reject, actor (or explicit system auto-review origin), nonblank rejection/correction reason, predecessor decision ID, and creation time. Serialize on Task then Response/QuestionResponse, require the expected current decision ID (null for first decision), and allocate an increasing per-outcome decision number. Use the required UUID request key defined above for every manual decision/correction, including each selected outcome in an atomic batch. A unique QuestionResponse/requesting-actor/request-key identity converges retries; mismatched content conflicts within that outcome, while another outcome can independently use the same actor/key. QuestionResponse already identifies its question, so no redundant question component is needed. Only projects frozen in `automatic` review mode append a system acceptance during submission for each answered outcome. In `manual` mode, answered outcomes remain pending with no decision until an authorized reviewer acts. Submitted skips are non-reviewable: reject any accept, reject, or correction request targeting a skip without appending a decision.

Manual review capability is distinct from collection ownership. A reviewer cannot review their own response, edit answer content, or change its pinned contract. A whole-response review action validates and persists one decision per selected answered outcome atomically; a selected skip or invalid request key rejects the entire batch with no decisions; no independent aggregate verdict obscures partial acceptance. Corrections append a successor rather than changing history. The latest decision is the effective verdict; a submitted answer without a decision is pending. Corrections after completion remain allowed for audit, but never resume allocation in a closed project.

TaskQuestionProgress stores accepted, pending, skipped, rejected, live-reservation counts, and attention state. Keep accumulated evidence counts (progress, failures, and item coverage) as native 64-bit database integers with integer arithmetic. Expose them as canonical nonnegative decimal strings through GraphQL String, including `"0"` for zero, with no sign, leading zeros, fraction, or exponent. Convert only at the API boundary; do not use floating point, narrow to GraphQL Int, or clamp counts to targets. This preserves excess accepted evidence from corrections without a custom scalar or lifetime evidence quota. Rebuild from Attempts/AttemptQuestions, submitted outcomes, and effective decisions; no duplicate reputation events. Cumulative submitted skips plus currently rejected answered outcomes plus expired/released attempts that offered a question form its failure count; deliberate cancellation does not. After every evidence change and during reconciliation, derive attention exactly when the accepted target is unmet and the current failure count is at or above the positive frozen threshold (default 5). Such questions are not newly offered; other questions can proceed. Corrections that reduce failures below the threshold clear attention even while the target remains unmet; meeting the target also clears attention. After every evidence change, derive Task state in order: satisfied if all question targets are met; otherwise cancelled if Project is completed/archived; otherwise needs_attention if all remaining unmet questions are escalated; otherwise open. Post-closure corrections can change this projection between satisfied and cancelled without reviving terminal attempts or reopening the project.

A manager holding both `tasks.assign` and `tasks.results.read` can use the existing audit task/attempt connections to select a previous terminal Attempt of that same task/project, then create a linked follow-up for an explicitly selected eligible worker. Recheck both capabilities on creation and retries. This reuses result inspection without an assignment-specific discovery endpoint or automatic predecessor selection; ordinary direct assignment remains assign-only. The selected worker may be the predecessor's worker or a different worker; the link preserves lineage rather than restricting reassignment. Reuse the existing allocation worker and predecessor fields and include both in request identity. This deliberately bypasses the same-task exclusion and attention gate for unmet questions, but never the selected worker's eligibility, the one-live-attempt limit, lease, or answer capacity. It creates fresh evidence and does not reset cumulative failures. Pool selection stays blocked while the derived attention condition holds; further follow-ups during that period remain explicit. If a correction clears attention while the target remains unmet, ordinary allocation can resume subject to the existing active-project, worker-eligibility, same-task exclusion, and capacity rules. This lets a manager recover escalated work when all prior workers are ineligible. There is no reopening fulfilled questions just to gather additional data in this release.

Update affected projections synchronously with evidence transitions. Oban reconciliation locks the same Task/coverage rows and replaces projections from authoritative evidence; it must not overwrite newer changes based on an earlier unlocked read. Reviewer decisions, not cached counts, determine exports.

### 9. Paginated GraphQL and immutable result exports

Expose explicit organization/project-scoped create/configure/activate/pause/resume/complete/archive, fetch/assign/follow-up/start/release/cancel, work-bundle/receipt, save/submit, review/correct, evidence-inspection, and request/read/download-export operations. Owners start/release their own live attempts; managers require `tasks.assign` to cancel another worker's live attempt, without receiving its work bundle. Use typed inputs/results and sanitized codes such as `invalid_project_configuration`, `unsupported_task_contract`, `attempt_expired`, `stale_response`, and `review_conflict`. Allocation distinguishes the no-work reasons above. A no-work response carries no arbitrary dataset data. GraphQL remains the only application API.

All lists and nested collections follow the existing Relay keyset pagination conventions. Explicit groups and presentations sort by position then ID; evidence sorts by immutable creation time/ID or decision number. The MVP adds no product-level cohort/group, enrollment/review batch, offered-question, answer/reason/explanation, annotation, or export count/byte ceilings. Decide additional sizing policy from actual usage in a later change. Preserve existing HTTP request handling, Assets/provider constraints, published Forms validation, scalar representations, and database operation timeouts. Activation checks the published contract without imposing a tighter execution ceiling. Positive answer/coverage targets and failure thresholds retain signed 32-bit GraphQL Int semantics; accumulated evidence counts, including export record totals, use the exact GraphQL String representation above. No aggregate query-complexity or quota machinery is added.

`tasks.results.read` permits accepted-result and audit inspection, including exact project/form/schema/revision/TaskInput identities, AttemptQuestions, actual display order, outcomes, source-value/label/option references and their immutable human-readable content, worker ID, timestamps, and decision history. Accepted results contain all effectively accepted answers; no consensus or truth layer. Audit also includes pending/rejected outcomes, skips, and terminal unsubmitted attempts (expired/released/cancelled). Do not include account email, authentication data, storage credentials, compensation fields, any unsubmitted draft payloads (including terminal drafts), or another organization's evidence.

New exports require an activated project (`active`, `paused`, `completed`, or `archived`) so the project's form/schema contract is already frozen. Reject draft requests before export/job persistence; they must not prevent ordinary draft repinning. Identical request-key retries still recheck current authority before returning existing exports.

ResultExport has `queued -> snapshotting -> writing -> ready|failed`, organization/project, requesting actor, mode, optional inclusive task-ID range, optional evidence kind and inclusive ID range within that kind, immutable snapshot time, counts, ready Asset, and sanitized error. The evidence-ID range requires an evidence kind; combine all supplied filters. This lets a caller partition outcomes, individual child rows, or review history within one task. Reuse immutable resource IDs and the existing bounded evidence connections to choose ranges; no partition scheduler or new cursor ledger. Enqueue via Oban transactionally with request creation. A UUID request key unique per project/requesting actor converges identical mode/filter requests and rejects conflicting arguments. Validate its UUID type before persistence or job enqueue; invalid input creates no export or job. Each requested partition has its own snapshot; separate requests do not promise a common snapshot.

At first processing, recheck organization activity and the requester's result capability, then use a repeatable-read snapshot to persist relational membership through paged reads and the immutable filters: Task IDs, terminal Attempt IDs, submitted QuestionResponse IDs, their effective ReviewDecision IDs (nullable for pending), and included ReviewDecision history IDs, only as needed for the selected output records. Pin referenced immutable presentation/definition/binding/value IDs once when selected as context, using their existing identities rather than copying their content into new product resources. Do not pin all outcomes or history merely to export one task's identity row. Immutable children can be selected from their pinned parents using those filters without copying each child into a new membership table. Include every selected output record, including children, decisions, and shared context, in the exact record count. Seal membership, counts, and `snapshot_at` atomically only after the entire selection succeeds; an operation failure rolls back the incomplete snapshot. There is no export-specific row ceiling. No timestamp cutoff or bare maximum sequence substitutes for committed snapshot membership. Once sealed, retries reuse the identical membership, even when reviews change. Export snapshots omit all unsubmitted draft payloads, project titles, current project/task status, and other unpinned mutable fields.

Stream stable ordered JSONL from immutable pinned entries outside the snapshot transaction. After one format-version/count header with exact decimal-string counts, emit one line per selected evidence row ordered by kind then immutable ID. ## Risks / Trade-offs

- **Collection still spans several workflows** -> Verify the phases in `tasks.md`, including text spans, review, and exports. Image-dependent work has its own complete follow-up rather than unfinished tasks here.
- **File delivery needs a configured adapter** -> Successful contract tests must exercise actual export bytes/sealing and fail-closed unsupported adapters. A real reachable adapter is a deployment requirement for file transfer; neither that integration nor detailed media is an implementation/archive gate here.
- **Hot allocation rows and finite selection search** -> Use skip-locked task/coverage reads, short transactions, and retryable contention outcomes. Measure before adding more scheduling state.
- **Snapshot and activation cost** -> Page through stored records and stream exports, retain existing operation timeouts and atomic rollback, and use actual usage to decide future limits. Larger projects or export partition automation require a later change.
- **Projection drift or review corrections** -> Preserve every authoritative record, lock during reconciliation, use pinned export membership, and never infer truth from a cached count.
- **Access descriptors outlive revocation briefly** -> Limit expiry to the lease and five minutes, recheck before issuing, and preserve the existing no-store/no-referrer contract.

## Implementation and operations

The implementation uses generated Ash resources and scoped AshPostgres foreign keys. Allocation, draft saves, submission, review, reconciliation, and completion share the documented Project/Task lock order. Completion uses Ash atomic bulk updates with indexed offered-question counts; it does not replay submitted answer or review history. The narrow direct SQL boundaries are PostgreSQL UUID issuance before ordinary asset registration, database wall-clock timestamps, and setting export snapshot transaction isolation before its first query.

Operators provision the existing Authorization capability catalog and selected role grants explicitly: `projects.read`/`projects.manage` govern configuration, `tasks.assign` governs ordinary assignment/cancellation, `tasks.review` governs decisions, and `tasks.results.read` governs result provenance and exports. Linked follow-up assignment requires both assignment and result access. Selecting draft source contracts also requires the existing Forms/Datasets read grants. No production capability or role is seeded by this change, and operator-bootstrap remains independent.

Oban runs lease cleanup and projection reconciliation on `task_maintenance`, and export generation on `task_exports`. Export adapters implement the optional streaming `write_staging` callback in addition to existing sealing, verification, and short-lived opaque access descriptors. Missing support produces a sanitized failure and preserves committed snapshot and pending-asset identity for retries. The in-memory adapter verifies these contracts without making a live HTTP delivery claim. Image requirements, image presentation/choice, and spatial answer contracts fail activation with `unsupported_task_contract`; the separate `add-project-task-media` change owns their implementation and acceptance gate.

A disposable PostgreSQL database was seeded with published Forms and Dataset revisions before applying the collection migrations. Additive migration preserved the original UUIDs, content fingerprints, and root-record references, after which a project, task, submission, automatic review, and sealed export membership were created. Both collection migrations were rolled down and reapplied, retaining the original published foundations. Review corrected generated mixed add/modify ordering and a redundant down-migration modification of a removed column. These down migrations intentionally remove collection evidence and are only a disposable-schema check: production rollback must retain the additive tables and real task/export evidence, pause affected work, and disable the new queues/API deployment rather than drop collected data.
