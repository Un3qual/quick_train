## Context

See `proposal.md` for motivation and scope. The source is `../record-future-product-architecture/design.md`, especially A and C–J, M–O. Authentication, normalized datasets/assets, and versioned forms are already implemented and archived. The current GraphQL schema includes those domains; Projects and Tasks do not exist.

Existing Forms exposes stable FormVersion, InputSlotDefinition, InputFieldRequirement, PresentationElement, QuestionDefinition, QuestionOption, and Label identities. Its typed constraints already define Unicode code-point spans and normalized spatial coordinates. Datasets provide single-valued flat records and immutable revisions. Assets currently certify only immutable bytes, not image dimensions or rendering safety. Existing resource policies and the shared OrganizationCapability check require organization membership for management. The external-worker route specified here is an explicit product relationship, never a relaxation of that shared check.

The user revised the release order: this change must be implementable and complete before detailed media support. Image presentation, image choice, spatial responses, and mask uploads are tracked in [add-project-task-media](../add-project-task-media/proposal.md). Only that follow-up depends on the separately scoped verified-media/storage foundation.

## Goals / Non-Goals

**Goals:** Keep canonical evidence relational and immutable, keep projections rebuildable, use existing Ash lifecycle patterns, and make concurrent allocation, submission, and review unsurprising. Each implementation phase is independently testable while the complete collection scope remains tracked here.

**Non-Goals:** A generic workflow engine, plugin registry, scheduling framework, event-sourcing layer, mutable project-version graph, or alternate identity/authorization system. No JSONB product content; Oban's own transport arguments remain ordinary framework infrastructure.

## Decisions

### 1. Two domains with named boundaries

`QuickTrain.Projects` owns project configuration and worker admission. `QuickTrain.Tasks` owns issued work, evidence, review, projections, and exports. Tasks depends on Projects, Forms, Datasets, and Assets. Projects depends on immutable Forms/Datasets definitions, not on task resource ownership. Project completion can invoke a narrow Tasks cancellation workflow in the same database transaction. Finance/Reputation get no placeholders or callbacks in this release.

Use generated Ash domains/resources, code interfaces, policy checks, transactional actions/changes, AshPostgres relationships and checks, and explicit AshGraphql allowlists. Keep named workflows near their owner: `Projects.ProjectActivation`, `Tasks.TaskSelection`, `Tasks.AttemptAllocation`, `Tasks.ResponseSubmission`, `Tasks.QuestionReview`, and `Tasks.ResultExport`. Use ordinary functions for shared type checks rather than a generic service layer.

Alternative: one large product domain would obscure ownership; more orchestration domains would add indirection without independent state. Two domains preserve the recorded dependency direction.

### 2. One frozen project is one collection run

| Owner | Persisted concept and essential fields |
| --- | --- |
| Project | organization, immutable key, title, dataset, published schema version, published form version, state, audience, external-access mode, selection/review modes, coverage target, lease duration, timestamps |
| ProjectItem | project, stable dataset item, exact revision; unique project/item |
| ProjectInputBinding | project, requirement, field definition; unique project/requirement |
| ProjectSlotPolicy | project, input slot, exact item count, shuffle flag |
| ProjectQuestionPolicy | project, question, accepted-answer target, skip allowed, reason required, failure threshold |
| ProjectWorkerAccess | project/user, disposition `allow` or `block`; absence is neither; unique project/user |
| ExplicitGroup / ExplicitGroupInput | authored group position and exact cohort-item/slot membership; never a pre-created Task |

A project pins exactly one published dataset schema version. Every cohort revision uses that version, so one binding per requirement is sufficient. Each item occurs once in the cohort, and a group uses distinct items across all slots. One fixed count per slot lies within the form's minimum/maximum; no runtime variable group sizes or slot-specific query language. Bind every requirement to an exact root field of the same family/cardinality. A required requirement needs a required field; optional requirements can bind required or optional fields. Every cohort item must satisfy each slot's bindings because the initial selector can place any cohort item in any slot.

Draft enrollment/removal uses explicit revision IDs in batches; it never interprets "latest" after activation. Activation locks Project, reloads all configuration/cohort pages, validates relationships, field readiness, complete policies, group feasibility, and bounded counts, and freezes everything except title, lifecycle, and worker-access overrides. Every configuration child edit takes that same lock and rechecks draft state. ProjectWorkerAccess remains mutable after activation so an allowlist can admit or revoke users; blocks always win. Audience and external-access mode themselves remain frozen.

Later enrollment or changed bindings/targets uses a new draft project with a new identity. No configuration versions, enrollment snapshots, or implicit carryover of task progress. A convenience clone operation is outside scope.

Lifecycle: `draft -> active`, `active <-> paused`, `active|paused -> completed`, `completed -> archived`. Pause prevents new allocations but permits live leases to finish. Completion deliberately closes remaining demand, atomically expires overdue live rows before cancelling unexpired live attempts and unsatisfied tasks, and keeps submitted responses reviewable. Completion itself preserves satisfied tasks; later review corrections recompute their state using the precedence below. Archive is a retention state, not deletion; managers can still inspect/export/review submitted evidence. Completion does not require coverage satisfaction or an unnecessary pause, and no automatic completion is inferred from a temporarily empty fetch.

Alternative: mutable configuration snapshots support continuous enrollment but introduce identity/version/transition machinery; new projects make the frozen contract explicit with existing lifecycle concepts.

### 3. Management and worker access are separate

Management capabilities are `projects.read`, `projects.manage`, `tasks.assign`, `tasks.review`, and `tasks.results.read`. All require the active account, owning organization, membership, and exact capability through the existing check. Each mutation authorizes its own returned result; manage/assign/review does not silently grant unrelated browse access. Selecting dataset and form resources during draft authoring also requires their existing read capabilities. Provision catalog entries and explicit role grants using existing operator primitives; do not auto-grant roles or depend on the separate operator-bootstrap change.

Worker eligibility is evaluated with explicit organization/project and the authenticated User, never a supplied worker ID for self-service actions. `organization_members` accepts active members; `external_users` accepts any active user through open access or that user's allow entry, even if the user is also a member; `both` is the union. A block overrides all routes. No geography, qualification, or reputation rules are introduced. Direct assignment requires `tasks.assign` for the caller and applies exactly the same eligibility/capacity checks to the target worker.

Every allocation rechecks current eligibility and an active project. Existing live attempts permit reads/writes while the project is active or paused, but still recheck account, organization, current audience route, block status, ownership, and lease. Membership removal only disqualifies a worker if no external route remains. Revocation rejects new work access without erasing evidence. Already-issued storage descriptors can remain usable until expiry; cap them at the earlier of five minutes and the lease deadline and never describe revocation as retroactively revoking signed URLs.

Tasks exposes a typed attempt work bundle with only pinned published form definitions, offered question IDs, actual input order, and bound values. It must not return generally browsable Form/Dataset/Asset resources with their authoring/reverse relationships. Use narrowly scoped Ash read actions and typed nonpersistent result resources where projections are needed. Any internal authorization bypass follows one explicit attempt-ownership check and selects by attempt/task/project IDs, not arbitrary user-provided resource IDs. No worker-provided context flag grants authority.

After a terminal attempt, workers can read a receipt containing their own attempt ID, state, timestamps, and review statuses, but cannot renew source access or change/read draft content through the work bundle. Receipt reads still require an active account/organization, ownership, and a current unblocked audience route; they do not require a live lease or an active project. Organization result readers retain evidence access. Omitted/foreign IDs fail with the same sanitized not-found/forbidden shape.

### 4. Issued groups, question capacity, and coverage

Task owns immutable TaskInputs (cohort revision and slot), TaskQuestionProgress, and Attempts. Tasks also owns one TaskItemCoverage projection per ProjectItem. Each Attempt owns immutable AttemptQuestions (the question set offered at allocation), AttemptInputPresentations (TaskInput, displayed position within slot), and one Response. AttemptQuestions is the small relational record needed to explain why an attempt answered only some form questions; it is not a question copy.

For each question, available capacity is `target - accepted - pending - live reservations`, floored at zero. Allocate an attempt only when at least one question has capacity and freeze exactly those question IDs. Each live AttemptQuestion reserves one unit; submitted answered outcomes become pending or accepted, while skips/expiry/release/cancellation release the reservation. Pending manual reviews therefore prevent over-issuing work. All offered questions, and only those, need explicit outcomes at submission. A later rejection opens capacity again. No cap truncates accepted evidence: a correction can cause accepted counts to exceed the target and every accepted answer stays visible.

Per-item coverage counts appearances in distinct issued TaskInputs, including issued tasks later cancelled, and is independent of answer replication. Retrying an existing task or creating follow-up attempts does not increment coverage. A balanced project's positive coverage target is a lower goal, not a hard upper bound: filling a group around an under-covered item can expose other items above target. Explicit selection requires its complete authored groups to cover every cohort item at least that many times before activation.

Task grouping identity uses slot IDs and sorted cohort-item IDs within each slot, separate from randomized presentation. Use a versioned length-delimited encoding and hash plus equality verification; enforce unique project/group identity. The same exact group is one Task with multiple attempts, not duplicate task rows. Reject duplicate explicit groups at draft authoring/activation. Never create unused random groups or deterministic generation schedules.

`TaskSelection` has a small internal strategy contract: given frozen project configuration, eligible candidate items/groups, and coverage, return a canonical group or a typed no-work reason. Dispatch only `balanced` and `explicit`; reject unknown modes. No persisted plugin registry or future algorithms.

Fetch and direct assignment first reuse open non-escalated tasks with question capacity that this worker has never attempted. Otherwise balanced selection anchors on an under-covered cohort item, fills each slot from least-exposed distinct candidates, samples ties afresh per fetch, and creates only the group issued. If a preferred group already exists, search alternative companions and exposure tiers within the request bound instead of repeatedly selecting that same group. Tie sampling must not create a stored random schedule. Once every item meets its coverage goal, balanced selection creates no more groups. Targets belong to exact task/question identities, so different groups cannot repair unmet targets on existing tasks; use other eligible workers or the existing deliberate follow-up path. Explicit selection consumes the next unissued authored group by position. Issuance and consumption commit together. Workers ordinarily never receive the same task twice, including after a skip, release, or expiry; deliberate follow-up is the sole exception.

Bound one selection transaction to 200 candidate groups. If contention or that bound prevents deciding, return `retry_later`; do not claim exhaustion. A complete scan finding no worker-specific work returns `no_work_for_worker`; all current demand being reserved/pending returns `waiting_for_answers`; proved coverage/group exhaustion with unmet demand returns `needs_attention`. Do not mark globally impossible work because one worker has exhausted eligible tasks. Selection tests assert these invariants, not a random sequence.

Alternative: pre-materialized pairs consume space proportional to combinations and invent evidence for work never offered. Fetch-time grouping stores only actual work.

### 5. Transaction order, leases, and retry identity

Use Ash transactions and locked scoped reads. Related-data checks happen after locks. Ordinary mutation paths hold a shared Project row lock; draft edits, admission overrides, activation, and lifecycle transitions take an exclusive Project lock. This lets lifecycle/admission changes serialize with worker commits without serializing all ordinary answers on the Project row. Lock order is Project, worker User (for allocations), existing Task/progress in stable IDs or new-group cohort coverage in stable IDs, Attempt, Response, QuestionResponse. A path selecting a new group does not return to existing-task selection while retaining coverage locks; retry from the start instead. Review and submission take Task before Response. Source FormVersion/revisions are immutable and need no write locks.

Use task/coverage `FOR UPDATE SKIP LOCKED` for competing selectors through the data layer's supported locking facility. Revalidate capacity and canonical-group uniqueness under those locks. When a supported Ash API cannot express the required locking or export snapshot isolation, a small parameterized query/transaction helper through the existing Repo is a justified boundary exception; business rules, resources, and writes still belong to Ash. No handwritten Ecto replacement, triggers, or stored business functions.

One live attempt per project/worker is enforced by locking the worker during allocation and a partial unique index on live states. Before inserting, transition any past-deadline live row for that worker to expired under its Task/Attempt locks so stale physical state cannot violate the index. Concurrent projects may briefly contend on that user's row, an acceptable first-release trade-off. Admission changes lock Project exclusively; account/organization/membership state is reread for each request. Authorization is evaluated at the transaction's authorization point; existing foundation status changes need not gain a new global lock protocol. Subsequent requests must see revocation.

Attempts start `claimed` (pool) or `assigned` (manager); start/first save makes them `in_progress`. Live states transition to `submitted`, `expired`, `released`, or `cancelled`; terminal states never revive. Lease duration defaults to 30 minutes, frozen on Project within 1–120 minutes; no heartbeat/renewal protocol. Enforce the deadline using database wall-clock time after acquiring locks, including a request that waited across expiry. A unique Oban expiration job is cleanup only; actions and capacity calculations ignore expired leases even before the job runs. Release, expiry, and cancellation retain stored draft rows but never expose their payloads as submitted or public audit evidence; audit access covers the terminal attempt, offered questions, and presentation. Completion holds the exclusive Project lock and takes one database wall-clock cutoff. In the project transition transaction, first expire physically live rows whose deadlines are at or before that cutoff, preserving their failure contribution; then cancel the remaining unexpired attempts and unsatisfied tasks and update reservations/progress. A lease crossing its deadline later during that transaction is classified at this same cutoff. No terminalization state is deferred to cleanup; failure rolls back the entire completion. The project lock prevents concurrent submit from committing after completion.

Use indexed set-based updates limited to affected attempt states, their offered-question reservations, and unsatisfied task/progress rows. Do not rescan submitted answers/review history, load the full project graph, or rebuild all projections during completion. Work grows with the affected live/overdue attempts and unsatisfied tasks; the exclusive lock can block project writes until commit. Retain finite database/operation timeouts and rollback on timeout. Operators may use the existing pause action and let leases finish/expire before retrying completion to reduce live work, but pause is not required. A new drain state, background cancellation workflow, or partial canonical completion is outside scope; measure this deliberate bulk operation before adding that machinery.

Allocation requires a 1–128 byte request key. Store it and normalized request identity on Attempt, unique per project/requesting actor/key; operation, target worker, and explicit follow-up target participate in the identity. A retry returns the same attempt's current receipt/bundle after current authorization and never renews it. Reusing a key for different arguments returns `idempotency_conflict`. A no-allocation result need not consume a key. Submit uses the Response identity: retry returns its existing immutable result. Draft saves replace one whole question outcome under the Response lock and require `expected_revision`; increment the response revision atomically and reject stale writes. Review uses its own decision identity below. No generic idempotency ledger is needed.

### 6. Typed drafts, skips, and text spans

One Response per Attempt transitions `draft -> submitted`. QuestionResponse is unique per response/question and stores `answered` or `skipped`, the family, and exactly the matching scalar columns or child relation. Text, integer, decimal, and boolean use nullable typed columns with local exclusivity checks; multi-valued answers use StaticOptionAnswer, TaskInputAnswer (ranking adds position), and TextSpan. Avoid four scalar wrapper tables with no independent identity. Foreign keys carry response/task/form-version scope where needed so a valid foreign UUID cannot bind a different graph. Dataset values and response values remain separate resources.

Submission locks Task, Attempt, and Response, rereads current lease/access and the complete offered question set, and validates every answer against the pinned published constraints. Reject missing outcomes, extra questions, incompatible typed children, duplicate choices/ranks, labels/options from another question/version, and TaskInputs outside the referenced slot. Ranking is a complete unique permutation of that slot's inputs. Preserve decimal precision, signed 32-bit integers, exact text and whitespace; reject NUL/non-finite numerics. Text constraints and spans count Unicode code points, not bytes or graphemes. Save may retain an incomplete answer, but must enforce local types, ownership, size limits, and no malformed children; submit enforces completeness/count bounds. Every child edit and delete locks the same Response; no stale record can bypass its frozen state.

Skipping is explicit and contains no answer children. If allowed by the frozen question policy, accept optional nonblank reason text (required when configured), optional explanation, and a server timestamp. Replacing an answer with a skip removes its draft children atomically; submitted skips never disappear. All-skipped submissions are valid where every offered policy allows them, satisfy zero answer targets, and contribute to escalation. Optional absent dataset values are represented as absent; required annotation/question source requirements are never silently synthesized.

Text spans reference TaskInput, its exact bound DatasetValue, and a label from the question's label set. They satisfy `0 <= start < end <= source code-point length`; overlaps are allowed, exact duplicate input/value/label/range tuples are rejected. Zero spans is a valid answered outcome only when the form minimum is zero. Text-span execution uses immutable text and has no image-format dependency.

Activation uses a closed supported-contract check over the entire published form. Reject any `image` input requirement (including one displayed through a `bound_value` element), `image_choice` renderer, or bounding-box/polygon/raster-mask family with `unsupported_task_contract`. Do not silently omit unsupported questions, call a media service, or enable them merely because a provider is installed. Their published Forms definitions remain valid; the later task-media change extends execution deliberately.

Do not generate spatial tables, mask-attachment resources, worker mask-upload actions, or media callbacks in this change. The follow-up owns their normalized geometry/provenance and verified-source integration. This keeps the first implementation complete with no permanently unchecked media tasks or speculative resource scaffolding.

### 7. Review and escalation preserve evidence

QuestionResponse has append-only ReviewDecisions containing accept/reject, actor (or explicit system auto-review origin), nonblank rejection/correction reason, predecessor decision ID, and creation time. Serialize on Task then Response/QuestionResponse, require the expected current decision ID (null for first decision), and allocate an increasing per-outcome decision number. A unique QuestionResponse/requesting-actor/request-key identity converges retries; mismatched content conflicts within that outcome, while another outcome can independently use the same actor/key. QuestionResponse already identifies its question, so no redundant question component is needed. Only projects frozen in `automatic` review mode append a system acceptance during submission for each answered outcome. In `manual` mode, answered outcomes remain pending with no decision until an authorized reviewer acts. Skips receive no accept decision.

Manual review capability is distinct from collection ownership. A reviewer cannot review their own response, edit answer content, or change its pinned contract. A bounded whole-response review action validates and persists one decision per selected question atomically; no independent aggregate verdict obscures partial acceptance. Corrections append a successor rather than changing history. The latest decision is the effective verdict; a submitted answer without a decision is pending. Corrections after completion remain allowed for audit, but never resume allocation in a closed project.

TaskQuestionProgress stores accepted, pending, skipped, rejected, live-reservation counts, and attention state. Rebuild from Attempts/AttemptQuestions, submitted outcomes, and effective decisions; no duplicate reputation events. Cumulative submitted skips plus currently rejected outcomes plus expired/released attempts that offered a question form its failure count; deliberate cancellation does not. At the positive frozen threshold (default 5), an unsatisfied question requires attention and is not newly offered; other questions can proceed. Satisfaction takes precedence over attention. After every evidence change, derive Task state in order: satisfied if all question targets are met; otherwise cancelled if Project is completed/archived; otherwise needs_attention if all remaining unmet questions are escalated; otherwise open. Post-closure corrections can change this projection between satisfied and cancelled without reviving terminal attempts or reopening the project.

A `tasks.assign` manager can create a linked follow-up referencing a previous terminal Attempt of that same task/project and explicitly selecting any currently eligible worker. The selected worker may be the predecessor's worker or a different worker; the link preserves lineage rather than restricting reassignment. Reuse the existing allocation worker and predecessor fields and include both in request identity. This deliberately bypasses the same-task exclusion and attention gate for unmet questions, but never the selected worker's eligibility, the one-live-attempt limit, lease, or answer capacity. It creates fresh evidence and does not reset cumulative failures. Pool selection stays blocked for escalated questions until accepted evidence reaches the target; further follow-ups remain explicit. This lets a manager recover escalated work when all prior workers are ineligible without a new attention-reset action. There is no reopening fulfilled questions just to gather additional data in this release.

Update affected projections synchronously with evidence transitions. Oban reconciliation locks the same Task/coverage rows and replaces projections from authoritative evidence; it must not overwrite newer changes based on an earlier unlocked read. Reviewer decisions, not cached counts, determine exports.

### 8. Bounded GraphQL and immutable result exports

Expose explicit organization/project-scoped create/configure/activate/pause/resume/complete/archive, fetch/assign/follow-up/start/release/cancel, work-bundle/receipt, save/submit, review/correct, evidence-inspection, and request/read/download-export operations. Owners start/release their own live attempts; managers require `tasks.assign` to cancel another worker's live attempt, without receiving its work bundle. Use typed inputs/results and sanitized codes such as `invalid_project_configuration`, `unsupported_task_contract`, `attempt_expired`, `stale_response`, and `review_conflict`. Allocation distinguishes the no-work reasons above. A no-work response carries no arbitrary dataset data. GraphQL remains the only application API.

All lists and nested collections use Relay keyset pagination, default 50/max 100. Explicit groups and presentations sort by position then ID; evidence sorts by immutable creation time/ID or decision number. Do not reintroduce aggregate query complexity controls removed by Forms; retain request and per-operation bounds. Initial application ceilings: 10,000 cohort items/project, 10,000 explicit groups/project, 100 total inputs/task, 100 IDs per enrollment write, 200 offered questions (the Forms ceiling), 1,000 text spans/question and 10,000 total text spans/response, 64 KiB answer text, 1 KiB skip/review reason, 16 KiB explanation, and 100 questions/review batch. Reuse the existing HTTP request-body cap and reject oversize input before large allocation/decoding. Activation rejects form minimums that cannot fit execution ceilings, but can execute a larger published maximum by applying the documented tighter execution ceiling. Positive answer/coverage targets and failure thresholds fit signed 32-bit Int; counts exposed publicly obey that scalar too and never wrap.

`tasks.results.read` permits accepted-result and audit inspection, including exact project/form/schema/revision/TaskInput identities, AttemptQuestions, actual display order, outcomes, source-value/label/option references and their immutable human-readable content, worker ID, timestamps, and decision history. Accepted results contain all effectively accepted answers; no consensus or truth layer. Audit also includes pending/rejected outcomes, skips, and terminal unsubmitted attempts (expired/released/cancelled). Do not include account email, authentication data, storage credentials, compensation fields, any unsubmitted draft payloads (including terminal drafts), or another organization's evidence.

ResultExport has `queued -> snapshotting -> writing -> ready|failed`, organization/project, requesting actor, mode, optional inclusive task-ID range, optional evidence kind and inclusive ID range within that kind, immutable snapshot time, counts, ready Asset, and sanitized error. The evidence-ID range requires an evidence kind; combine all supplied filters. This lets a caller partition outcomes, individual child rows, or review history within one task. Reuse immutable resource IDs and the existing bounded evidence connections to choose ranges; no partition scheduler or new cursor ledger. Enqueue via Oban transactionally with request creation. A 1–128 byte key unique per project/requesting actor converges identical mode/filter requests and rejects conflicting arguments. Each requested partition has its own snapshot; separate requests do not promise a common snapshot.

At first processing, recheck organization activity and the requester's result capability, then use a short repeatable-read snapshot to persist bounded relational membership and the immutable filters: Task IDs, terminal Attempt IDs, submitted QuestionResponse IDs, their effective ReviewDecision IDs (nullable for pending), and included ReviewDecision history IDs, only as needed for the selected output records. Pin referenced immutable presentation/definition/binding/value IDs once when selected as context, using their existing identities rather than copying their content into new product resources. Do not pin all outcomes or history merely to export one task's identity row. Immutable children can be selected from their pinned parents using those filters without copying each child into a new membership table. Count every selected output record, including children, review decisions, and all shared context, toward the same combined 100,000-record cap before sealing; stop at 100,001 and roll back rather than traverse an unbounded selection. Seal membership, counts, and `snapshot_at` in one transaction only when the total fits 100,000. No timestamp cutoff or bare maximum sequence substitutes for committed snapshot membership. Once sealed, retries reuse the identical membership, even when reviews change. Export snapshots omit all unsubmitted draft payloads, project titles, current project/task status, and other unpinned mutable fields.

Stream stable ordered JSONL from immutable pinned entries outside the snapshot transaction. After one bounded format-version/count header, emit one line per selected evidence row ordered by kind then immutable ID. Core kinds are `task`, `task_input`, `attempt`, `attempt_question`, `attempt_input_presentation`, `question_response`, `static_option_answer`, `task_input_answer`, `text_span`, `review_decision`, `presentation_element`, `question_definition`, `question_option`, `label`, `project_input_binding`, and `dataset_value`. Default exports include the pinned published PresentationElement sequence (original ID, form-version ID, kind, position, plain text, and question/requirement references), referenced question key/prompt/family, option key/label, label key/text, frozen bindings (slot/requirement/field identities and keys), and exact typed bound values. Combine published presentation elements with each eligible attempt's recorded offered questions and input order to interpret instructions, headings, sections, and bound-value/question placements. Definitions referenced by that presentation are context even for unoffered questions; their excluded response payloads remain excluded. Shared context uses existing immutable IDs and flat records counted toward the same combined 100,000-record cap and artifact byte limits as answers. There is no separate context allowance or copied per-attempt presentation resource. Result-scoped typed reads expose this same content with only `tasks.results.read`, including exact bound-source asset metadata/download issuance; they cannot traverse unrelated definitions or unbound/unissued source content. An explicit kind/range filter may omit context, which remains retrievable through the same scoped reads or context-kind exports. Do not embed asset bytes or expiring URLs. Each row carries its owning project/task/attempt/outcome IDs as applicable and exact referenced provenance IDs; do not expand related collections inside it or implicitly add rows outside the requested filters. Accepted mode includes evidence supporting effectively accepted outcomes and their pinned effective decisions; audit additionally includes submitted nonaccepted outcomes, terminal attempts, and review history. Deduplicate shared evidence by kind/ID. Preserve authored/display/decision order as explicit fields, decimals as exact strings, and hashes as hexadecimal. JSONL is an output format only. Cap output at 256 MiB or the stricter configured asset limit; use bounded temporary storage and cleanup, never load an entire export into memory. Publish through the existing Assets seal/verify protocol and then atomically associate one canonical ready asset. Add the smallest provider-neutral server-side staging-write capability needed for this workflow; an adapter without it returns `export_storage_unavailable`. Implement it in the in-memory test double for contract tests, not as a pretend reachable HTTP service. Provider selection and real HTTP delivery remain separate work.

Export read/download rechecks current results capability and organization activity. Assets must check ownership through export links before generic read/access or canonical reuse: `assets.read`/`assets.manage` alone cannot expose content solely owned through task results. Hash-only registration is not independent proof of source authority. An independently authorized pre-existing source or independently verified upload of identical bytes can grant byte access without exposing the result association. Keep task-generated assets linked to their export from registration onward, including pending publication, so a temporarily unattached asset never opens an authorization gap. Signed download access remains short-lived and opaque. Repeated jobs reuse sealed bytes/snapshot identity, and failures expose no partially published download. Do not automatically rerun a failed export against newer evidence under the same ID.

Result and export GraphQL responses inherit `Cache-Control: no-store` from the existing `QuickTrainWeb.Authentication.RequestSecurity` plug, including denials. Cover the new operations through the existing endpoint in `test/quick_train_web/graphql/project_task_collection_test.exs`; no additional caching middleware is needed.

### 9. Implementation layout and validation

Create `lib/quick_train/projects.ex`, `lib/quick_train/projects/` resources/workflows, `lib/quick_train/tasks.ex`, and `lib/quick_train/tasks/` resources/workflows/workers. Extend `config/config.exs`, `lib/quick_train_web/graphql/schema.ex`, and the specific Forms/Datasets/Assets boundaries above. Use `mise exec -- mix help ash.gen.domain`, `ash.gen.resource`, `ash.codegen`, and `ash_postgres.generate_migrations` to check installed generator options before invocation. Keep exact pinned dependencies unchanged unless a concrete integration requires a separately justified update.

Meaningful tests live in `test/quick_train/projects_test.exs`, `task_allocation_test.exs`, `task_responses_test.exs`, `task_review_test.exs`, `task_results_test.exs`, and `test/quick_train_web/graphql/project_task_collection_test.exs`, with shared scoped fixtures in `test/support/`. Concurrency tests use independent connections and explicit barriers for claim/claim, save/submit, submit/expiry/completion, review/review, correction/export, and reconciliation/evidence races. Assert state/provenance, not implementation text or exact random selection. Test direct Ash calls and GraphQL so resolver-only checks cannot masquerade as authorization. Finish with OpenSpec validation and the full repository verification gate.

## Risks / Trade-offs

- **Collection still spans several workflows** -> Verify the phases in `tasks.md`, including text spans, review, and exports. Image-dependent work has its own complete follow-up rather than unfinished tasks here.
- **File delivery needs a configured adapter** -> Successful contract tests must exercise actual export bytes/sealing and fail-closed unsupported adapters. A real reachable adapter is a deployment requirement for file transfer; neither that integration nor detailed media is an implementation/archive gate here.
- **Hot allocation rows and finite selection search** -> Use skip-locked task/coverage reads, short transactions, and retryable contention outcomes. Measure before adding more scheduling state.
- **Snapshot and activation size** -> Enforce explicit finite cohort/export ceilings and bounded paging; reject oversized requests atomically. Larger projects or export partition automation require a later change.
- **Projection drift or review corrections** -> Preserve every authoritative record, lock during reconciliation, use pinned export membership, and never infer truth from a cached count.
- **Access descriptors outlive revocation briefly** -> Limit expiry to the lease and five minutes, recheck before issuing, and preserve the existing no-store/no-referrer contract.

## Migration Plan

1. Generate additive AshPostgres migrations and snapshots with same-organization/project/task/version composite references, uniqueness, local scalar checks, selection indexes, and a live-attempt partial unique index. Existing dataset/form/asset IDs and content stay unchanged.
2. Register domains, workers, and explicit API actions. Provision capability catalog entries without automatic role grants; operators deliberately grant the new permissions. No collection starts until a manager activates a valid project.
3. Verify migration up/down/reapply on representative existing forms/datasets and new draft/active/submitted evidence.
